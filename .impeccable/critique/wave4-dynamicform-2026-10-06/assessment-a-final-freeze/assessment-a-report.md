# Assessment A：DynamicForm 文档页设计评审

**范围**：`http://127.0.0.1:4174/components/lxdynamicform.html`，包括 DynamicForm 文档、交互 Demo 与 LxUpload 状态。此报告只记录独立设计评审；未读取 Assessment B、detector/overlay 输出或其他代理报告。

**设计具体性**：中等，具备组件文档的领域适配，但视觉语言仍偏通用。任务表单、候选人员、单张/多张附件等内容让示例贴合 LinkX 管理后台；props、schema、events 参考表和可展开的字段预览也服务于组件使用者。主体沿用常见 VitePress 文档结构与 Element Plus 控件，品牌辨识主要落在蓝色主按钮，尚未形成独特的 LinkX 表达。

**总体印象**：这是一份覆盖较全、能直接操作的组件说明。校验和上传失败都有可见文案与恢复路径；主要负担来自长篇参考内容与移动文档外壳对演示区的潜在遮挡。移动遮挡判断来自一次 Demo 元素截图，可能受文档壳层影响，需在合并评审时与另一条独立浏览器证据核对。

## 认知负荷与情绪路径

认知负荷清单有 2 项未通过（8 项中）：

- [ ] **单一焦点**：初始演示可聚焦表单；展开“演示设置”和“字段类型预览”后，布局/禁用/主题、候选 Mock 状态、任务表单与字段示例同时争夺注意力。
- [ ] **信息分块**：props、schema、events 和用法依次铺成长参考页；主题标题能导航，但 schema 表仍需较多连续扫描。
- [x] **分组**：任务信息、附件、字段预览、演示设置各自成组。
- [x] **视觉层级**：分区标题、必填星号、错误色与主次按钮建立了清楚层级。
- [x] **一次一个决策**：初始状态把设置和字段预览折叠；用户可以先看默认表单。
- [x] **选择数量**：截图中单列/1/2/3 列为 4 项；候选状态为加载中/成功/空/失败 4 项。没有观察到同一决策点同时呈现超过 4 个选项的状态。
- [x] **工作记忆**：字段标签、上传限制和错误提示都靠近操作位置。
- [x] **渐进披露**：示例设置与字段预览按需展开。

任务本身有动态 schema 和远程数据等固有复杂度。代码/表格帮助开发者学习，但长参考页仍增加外在负荷。情绪路径较稳定：空表单提供明确入口，提交后必填错误就近出现；上传失败显红并保留文件及重试入口；成功只给简短校验反馈，符合管理工具的克制语气。最容易产生挫败的是在窄屏阅读时被文档导航遮住示例区域。

## 优点

1. **状态覆盖可教学**：必填错误、表单成功、上传中/取消/失败/重试成功、多文件成功及候选预览失败/恢复都有可观察样例，不只展示理想状态。
2. **恢复动作贴近问题**：错误靠近对应字段或文件；失败上传保留原条目，用户可以直接重试。
3. **默认示例有良好渐进披露**：设置和 schema 预览默认折叠，先呈现可读的任务表单；字段说明同时给出标签、必填和附件限制。

## 优先问题

### [P1] 移动端文档导航可能覆盖 Demo 字段

**依据**：`mobile-375-light-demo.png` 中，“Menu / On this page”横条落在表单中段，遮住字段区域；这可能是文档壳层或元素截图定位造成，尚未有独立 viewport 状态核实。整体页面宽度未溢出，但截图中的遮挡会妨碍开发者检查移动表单。

**建议**：让移动目录控件停靠在视口边缘并为演示内容保留空间；在正式结论前由综合评审用独立浏览器视图确认遮挡是否真实存在。可考虑 `/impeccable adapt`。

### [P2] “全部清空”触控区域偏矮

**依据**：移动视口的 DOM 几何测量中，`.lx-upload__clear` 为 56×18 px；同一组底部按钮为 86×44、60×44 px，单文件移除为 44×44 px。文字链接明显更难单手点中。

**建议**：保留紧凑视觉样式，同时将可点击区域扩到至少 44×44 px。可考虑 `/impeccable harden`。

### [P2] 长参考页增加定位和扫描成本

**依据**：文档页把安装/示例、props、schema、events 和用法连续排在同一条长阅读路径上；右侧目录降低了跳转成本，但窄屏仍需反复滚动表格与说明。

**建议**：为快速接入路径提供短的起步区，把完整字段/事件矩阵留作可定位的参考区；长表格在窄屏内滚动，不扩大整页横向尺寸。可考虑 `/impeccable distill`。

### [P3] 示例的产品辨识度仍弱

**依据**：组件能力本身覆盖具体业务，但蓝灰 Element Plus 外观与常见后台 Demo 接近，除了“任务/负责人/附件”的文案外不容易识别 LinkX。

**建议**：优先通过 LinkX 主题令牌、真实后台常见字段组合或更清楚的品牌导航建立辨识度，不增加装饰性视觉元素。可考虑 `/impeccable polish`。

未发现需要评为 P0 的设计阻断项。

## Persona 风险

**Jordan（首次使用者）**：任务字段和必填反馈容易读懂；上传限制也贴近上传入口。开发者若只想知道“从最小 schema 怎么开始”，需要自行从较长的参考页找到最短路径，缺少明确的快速接入引导。

**Sam（依赖辅助技术）**：截图可见字段标签、错误文字和状态文字，信息没有只靠颜色表达。图标按钮的可访问名称、键盘完整路径、焦点顺序、读屏播报及 4.5:1 对比度未在 Assessment A 中验证；浏览器状态快照还出现多个无可见文字按钮，但没有采集其 accessible name，因此这些是待核验风险而非已确认缺陷。

**Casey（移动端分心用户）**：375px 下全页没有横向溢出，表单字段堆叠且主要底部按钮达到 44px 高；附件移除按钮为 44×44px。`全部清空`仅 56×18px，命中面积偏小；移动 Demo 截图还显示目录横条可能覆盖输入区域。

## 次要观察与待讨论问题

- 成功状态位于表单底部操作区旁，错误则在字段附近；这让校验成功与失败的反馈位置不完全一致。
- 上传文件名、状态、大小及移除操作集中在一个条目中，信息清楚；失败态大面积浅红底比成功态更醒目，层级合理。
- 是否能把“快速接入”与“完整字段参考”分成两条明确入口，同时保留当前完整示例？
- 移动端目录横条是否只在文档阅读时出现，进入 Demo 操作区域后应否自动收起？

## 浏览器证据与覆盖边界

- 目标页面在 1440×1000 桌面及 375×812 移动视口返回 HTTP 200。使用 Playwright 驱动的系统 Edge 完成单轮采集。
- 14 条证据步骤中 11 条成功，3 条失败：桌面 HUD、负责人候选的主表单失败/空结果、移动 HUD/日期范围。失败来自 Playwright 操作隐藏的 Element Plus 原生 checkbox/radio 后未能改变状态或目标落在视口外；没有为这些状态继续重试。因此本报告不对 HUD 和主表单候选失败/空态下结论。
- 有效截图覆盖默认页/表单、必填错误、表单成功、上传中/取消/失败/重试成功、多文件成功、候选预览失败/恢复和移动默认页。逐图见 [截图索引](./screenshot-index.md)。
- 控制台记录 1 条未映射到具体请求的通用 404 错误，以及 1 条 Demo 预期的 `UploadAjaxError: 文档 Mock 上传失败`。本轮 `pageErrors`、`httpErrors`、`failedRequests`、`externalRequests` 均为空；页面未记录外部请求。404 的资源 URL 未捕获，不能据此判定用户可见资源缺失。
- 移动视口 `documentElement.scrollWidth/clientWidth` 均为 375；`main` 为 351/327，存在 24px 的主内容内部溢出，但没有整页横向滚动。其来源未能从 Assessment A 证据确定。
- 没有运行键盘/读屏辅助技术审计，也没有执行色彩对比测量；相关 persona 风险只列为待验证项。
