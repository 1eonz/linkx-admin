# LxSwitch 独立设计评审（Assessment A）

## 方法与范围

独立设计评审；实际打开全新浏览器页 `http://127.0.0.1:4192/components/lxswitch.html`，并检查桌面与 390px 窄屏。另以本机 Edge 的全新 Playwright browser context/page 保存截图。参考 `design/表单控件八件套/code.html` 第 07 节、对应 `screen.png`、LxSwitch 源码及中文 API/Demo。未运行 detector，也未读取 Assessment B 输出或旧 Critique 报告。

截图位于本目录：`lxswitch-desktop.png`、`lxswitch-mobile.png`、`lxswitch-demo-desktop.png`、`lxswitch-demo-mobile.png`、`lxswitch-props-mobile.png`。

## 设计特异性

**中等偏高，产品例子明确，控件骨架仍是通用开关。** 第 07 节给出 40×20 胶囊、16px 滑块、开启绿/关闭灰，并以卡口研判、夜间静默、上级锁定呈现 LinkX 场景；组件固定几何与颜色，并保留了这些文案。默认胶囊内文案是相对标本的有意扩展（`index.vue:25-26`、`style.css:37-51`），Demo 也明确分开展示内嵌、外置和两侧文字模式。品牌特征主要来自设计令牌和业务内容；单看开关形态，仍可原样用于其他 Element Plus 后台。

## 认知负荷

桌面 Demo 的八项认知负荷检查为 **0 项失败（低）**：示例按用途分组，每组最多四项；每个开关只有开/关两个选项；状态说明与控件同屏，源码示例另用折叠面板收起。没有单个决策点超过四个选项。窄屏两侧文案换行属于可读性问题，见优先问题，不增加选项数量。

## 情绪旅程

用户从简短介绍进入分组 Demo，先看到真实业务用语与清晰开关形态，预期容易建立。禁用态的“上级锁定”解释能减少误操作疑虑。加载示例出现 spinner 后，结尾却播报“省厅镜像同步 已开启”，实际 switch 的可访问状态仍是关闭；这让用户在最后一步失去对组件和 Demo 的信任，是本页最明显的情绪低谷。

## 优势

- 第 07 节的几何和状态色被明确固化，业务用语也延续自参考标本（`design/表单控件八件套/code.html:677-718`）。
- Demo 覆盖正常、禁用、无文字、loading、自定义值和两侧文字，且分组标题说明各自用途（`linkx-fe/src/components/LxSwitch/demo/basic.vue:49-169`）。
- 组件有键盘焦点环、触屏 44px 命中区，并将 `aria-describedby` 传到内部 switch；中文 API 也记录了这些行为（`style.css:71-85`、`index.vue:44-47`、`docs/components/lxswitch.md:62-64`）。

## 优先问题

### [P1] Demo 中可见标题没有成为 switch 的可访问名称

`demo/basic.vue:52-62` 把“卡口车辆实时 AI 研判拦截”放在独立 `div`，紧随其后的 `<LxSwitch>` 未传 `aria-label`，也没有 label/id 关联；夜间、锁定、值守和无文字示例也采用相同做法（`69-104`、`114-127`）。实际浏览器无障碍树中这些控件仅读作 `switch`，没有 Description。组件只同步 `aria-describedby`，虽然 `$attrs` 能透传 `aria-label`，Demo 并未提供它（`index.vue:44-47,65`）。这会让使用读屏的调用者无法分辨哪个设置将被切换，也会把缺少名称的集成方式当成范例。

**建议：**用语义标签关联每个控件，或给每个 `<LxSwitch>` 设置准确的 `aria-label`；在可访问性文档中明确开关必须有名称。

### [P2] loading 示例播报开启成功，但实际值仍为关闭

loading 项固定传入 `:model-value="false"`，事件处理器只更新 `lastAction`（`demo/basic.vue:133-139`；计时结束逻辑在 `24-37`）。我实际点击后等待 2 秒，页面播报“省厅镜像同步 已开启”，无障碍树的 switch 值仍是 `0`，控件也回到未选中。这让用户看到的结果与成功消息相反，直接拉低系统状态可见性。

**建议：**用响应式值控制该示例，并在模拟下发成功后更新值；如果模拟失败，则保持关闭并播报失败原因。状态文字必须与控件最终值一致。

### [P2] 窄屏两侧文字模式把状态词挤成窄列

在 390px 截图中，“未联动/已联动”挤在开关与说明之间并逐字换行（`lxswitch-demo-mobile.png`）。对应内容位于 `demo/basic.vue:155-167`，`.lx-switch-demo__pair` 仅用单行 flex 和固定 gap，没有窄屏重排（`248-252`）。用户难以快速读出当前状态，尤其是单手查看时。

**建议：**在窄屏把说明移到下一行，并让状态词保持不收缩；必要时让“两侧文字”示例单独占满一行。

- **Sam（键盘/读屏用户）：**切到示例后能找到 switch，但读屏没有业务名称；“卡口研判”与“夜间静默”无法区分。对应上方 P1。
- **Casey（移动用户）：**390px 下两侧文字模式状态词被拆行，说明文本与开关争宽；44px 触控尺寸是正面保障，但不能弥补标签难读。对应上方 P2。
- **Alex（熟练用户）：**单开关本身没有多余步骤；loading 示例强制等待 2 秒，结束还报告与控件相反的状态，成为可避免的延迟与确认成本。对应上方 P2。

## 次要观察

- `docs/components/lxswitch.md:25-33` 的 Props 表在 390px 下内容宽约 624px、可视宽 342px；标准表格支持横向滚动，但页面没有明显提示，`lxswitch-props-mobile.png` 中默认值和说明暂时在视口右侧。可给表格增加滚动提示，或为窄屏改用逐项定义列表。
- 标本 07 主要以胶囊外部“开启/关闭”文字表达状态（`code.html:682-699`）；Lx 默认 `inlinePrompt: true` 则把状态文字放入胶囊。文档已解释这是有意扩展，且另有无文字标本形态，因此不列作缺陷；维护者需要保持这个“标本对齐形态”和“Lx 默认形态”的区别清晰。

## 可启发问题

- 哪个形态最适合成为默认：标本的外置状态词，还是 Lx 的内嵌文案？调用者是否能从文档一眼判断何时用哪种？
- loading 演示能否在结束时同时更新真实值和状态播报，让用户亲眼看到完整的等待—成功闭环？
- 可否把“每个开关都有可访问名称”纳入 Demo 的组件使用约定，而不是只演示控件本身的键盘能力？
