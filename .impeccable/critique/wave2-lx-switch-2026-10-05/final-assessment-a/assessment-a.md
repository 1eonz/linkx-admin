## 设计特异性判定

整体设计特异性较强。示例文案落在 LinkX 的视频巡查与联防调度场景：卡口 AI 研判、夜间静默布防、省厅联防镜像；锁定态也沿用标本 07 的“上级锁定”语义。控件尺寸、色值和状态外置方式与 `code.html` 第 07 项吻合。文档外壳仍是标准 VitePress，开关仍是 Element Plus 风格，因此辨识度主要来自业务场景、状态设计和标本契约，而不是独有的视觉造型。

## 整体印象

这是一个能让开发者直接比较状态的组件说明页：主形态先呈现，扩展形态分组说明，失败模拟也有明确的恢复路径。最大的提升机会是让 HUD 模式的辅助文字达到可读对比度，并让窄屏 API 信息更容易横向比较。

## 做得好的地方

- 主形态准确复用标本 07：40×20 胶囊、外置“开启/关闭”、上级锁定说明，成功绿和信息灰也与设计源一致。
- 状态没有只靠颜色表达。关闭、开启、已锁等词在控件旁；锁定态禁用；loading、失败和重试成功均有可读反馈。
- 组件文档覆盖默认值、事件、旧 EP props 透传、无障碍和宿主适配。窄屏 Props 区明确写出“横向滚动”，现场也确认表格自身可以横向移动。

## 认知负荷

按 Critique 的 8 项检查，7 项通过、1 项部分不通过，整体负荷偏低。单个状态组最多同时展示三个开关，低于四项建议上限；每个变体有标题和相邻说明，用户不必一次理解所有状态。唯一的渐进披露弱点是主形态、胶囊内文字、无文字、加载态、两侧文字和多张 API 表都在同一长页中展开，窄屏用户需连续滚动才能抵达特定变体。当前折叠的仅是示例源码，复杂变体本身仍全量展开。

## 情绪旅程

用户先看到具体的标本和业务语境，能快速确认这是一种状态控制。锁定行解释了为何无法改动，减少“控件坏了”的疑惑。Demo 明示首次操作会失败，实际失败后也保留关闭值并提示可重试；第二次重试转为开启并播报结果，情绪低点短且可恢复。HUD 深色模式下，辅助说明和锁定行明显变暗，是这条旅程中最影响信心与可读性的部分。

## 优先问题

### [P2] HUD 辅助文字和锁定说明对比不足

**为什么重要：** 390px HUD 截图中辅助说明只有 11px。当前样式文字色为 `rgb(100, 116, 139)`，在半透明深色行底上的对比约为 3.48:1；锁定行再对整行应用 0.6 opacity 后约为 2.07:1。两者都低于小号正文的 4.5:1 目标。锁定原因正是用户理解权限边界所需的信息。

**建议：** 保留开关本体的禁用视觉，但不要降低整行文字不透明度；为 HUD 辅助文案选更亮的令牌，并对锁定说明单独校验对比度。

**建议命令：** `/impeccable polish`

### [P2] 窄屏 Props 表比较字段费力

**为什么重要：** 390px 首屏只能看到“名称/类型”两列；横向滚动后才能看到默认值和完整说明。滚动提示存在，但说明列文本变窄后产生很高的行，开发者需要同时横移和纵向扫读。现场横向滚动可用，问题在于信息比较成本，而非表格无法操作。

**建议：** 窄屏下固定名称列，并给其余列清楚的滑动边界；或者改成按属性堆叠的定义列表，让名称、默认值、说明在一个纵向块内连续阅读。

**建议命令：** `/impeccable adapt`

### [P3] 375px 首屏的主要示例出现较晚

**为什么重要：** 375×812 视口中，标题和较长的组件简介占据上半屏，交互示例标题约在 y=535，首个状态行约在 y=680；首次打开只能看到部分主形态。它是组件说明页的核心内容，用户需要先滚动才能操作。

**建议：** 将简介压缩为一段短摘要，把颜色、尺寸和 `LxStatusSwitch` 适配细节放到后续说明；让交互示例更早进入首屏。

**建议命令：** `/impeccable distill`

## Persona 红旗

- **Sam（键盘与屏幕阅读器用户）：** AX 树为各开关提供了可访问名称；锁定项暴露 disabled，错误用 `role="alert"`，Tab 焦点环可见。主要红旗是 HUD 11px 辅助文字对比不足，尤其锁定行整体变暗后，权限原因更难读。放大缩放和读屏播报未在本次独立视觉评审中单独验证。
- **Casey（分心的移动用户）：** 375px、390px 下整页没有水平溢出，单个开关区也能正常换行。查看 Props 时需主动横滑，且长说明行变高；首次进入时主控件在首屏下半部，容易被上方简介挤出注意力。
- **Jordan（首次集成者）：** 主形态的开启/关闭语义和锁定原因清楚。后续透传章节的 `attrs`、`EP`、`inlinePrompt` 等术语要求开发者读上下文；开发者目标受众能接受，但可在第一次出现时扩写 `EP` 为 Element Plus。

## 次要观察

- 375px 与 390px 页面内容都在视口宽度内，当前移动导航收纳为 Menu 与 On this page，不会遮住正文。
- 首次失败模拟文案在操作前已说明“首次失败、关闭值保留、再次成功”；真实交互表现与说明一致。该模拟只证明演示反馈，不证明业务后端行为。
- 设计对齐说明的技术细节有助于组件维护，但可与用户操作说明分层，减少主阅读流的篇幅。

## 可供后续讨论的问题

- HUD 模式是否也应把禁用原因维持在 WCAG AA 对比度，而不是沿用整行淡化效果？
- 窄屏 Props 页更需要保留原生表格，还是更需要把每个属性改为连续的移动端定义块？
- 对组件文档而言，首屏应优先展示可操作的主形态，还是优先解释完整的视觉契约？
