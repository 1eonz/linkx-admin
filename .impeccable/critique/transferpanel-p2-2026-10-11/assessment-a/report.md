人工取证已完成。使用本地 VitePress `http://127.0.0.1:4174`，通过独立 Chromium 新标签检查了桌面、窄屏、长文本、HUD 主题、键盘和减少动效状态。

- TransferPanel：1440px 下检查 Demo 默认 240px 和标准 380px；390px 与 320px 下检查待选/已选切换、批量操作、首屏行数和长名称；滚动到已选列表底部检查未加载项与“查看全文”。
- VirtualTree：1440px 下检查默认收起和展开“演示状态和更多操作”后的内容；390px 下检查收起状态对树首屏的影响。
- 键盘：树节点获得焦点后 `ArrowDown` 移到下一行，`Space` 改变勾选；已选项移除按钮按 `Enter` 后焦点移动到下一项。
- 减少动效：`prefers-reduced-motion: reduce` 下检查 TransferPanel 关键节点，浏览器计算出的过渡时长为约 `0.00001s`，没有观察到会阻塞操作的动画。
- HUD：Demo 的预览区域切换为深色背景和面板令牌，文档站外壳仍保持浅色；这与文档中“只作用于组件预览容器”的说明一致。
- 320px：页面 `scrollWidth` 小于视口宽度，没有发现页面级横向溢出；已选条目仍保留 44px 移除触控区，但首屏只显示前三条及滚动提示。

## Design Specificity Verdict

整体是为 LinkX 权限管理和公安机构树场景定制的界面：机构编码、在线/处理中/停用状态、未加载授权、下级继承和 5:2:5 穿梭布局都能在设计标本中找到对应关系。它不是可以原样套到任意后台的无主题双栏控件。

当前版本的主要偏差来自文档 Demo 的首屏基准。设计标本使用 380px 高度并展示约五条紧凑已选项；Demo 默认选择 240px，1440px 截图只让右侧列表看到两条，390px 截图看到三条后立即显示滚动提示。组件本身的 380px API 默认值仍然正确，但示例第一印象把“紧凑压力测试”放成了主路径。

## Overall Impression

组件的业务语义、状态反馈和键盘骨架已经成形，标准 380px 状态也能清楚地表达“树中选、右侧核对、逐项移除”的主流程。最大的机会是把示例的视觉基准拉回设计标本，并把批量操作和长文本入口的层级说清楚；现在用户需要从一组很小的文字和滚动提示中自己拼出动作范围。

## Cognitive Load Assessment

共 3 项失败，属于中等认知负荷。最明显的超限决策点是“打开 Demo 设置后的 4 个状态 + 3 个参数 + 高度选择”；这对开发者验证状态有用，但不应成为文档读者理解主流程的必要步骤。

## Emotional Journey

- **进入**：默认折叠设置、面板标题和数量计数让用户能直接进入权限选择，信任感较好。
- **操作**：筛选和批量按钮能反馈范围，上限原因也会被播报；但 240px 中栏的多行小字会让“为什么不能全部加入”变成阅读任务。
- **核对**：标准高度下右侧四条已选项与编码/状态并列，核对节奏清晰；窄屏下第三条后出现滚动提示，能避免用户误以为只有三条。
- **风险点**：长名称和未加载历史项在首屏被折叠或滚出，桌面只显示 chevron，用户可能错过完整名称入口。
- **收尾**：清空确认、状态消息和 Demo 撤销能减少后悔；真实保存成功/失败仍应由宿主在组件下方补齐。

## What's Working

1. **业务信息密度有依据**：名称、编码、状态和未加载键值被分成可扫描的层级，状态不只依赖颜色，符合权限审计核对场景。
2. **窄屏交互保持可操作**：390px/320px 下分段切换和移除按钮达到 44px 触控目标，320px 没有页面横向溢出，长名称默认两行且可展开。
3. **键盘与反馈链路完整**：树的方向键、Space/Enter、可见焦点、滚动剩余提示和 aria 描述形成连续反馈；减少动效状态下过渡被压缩，不会把焦点移动隐藏在动画里。

## Priority Issues

### [P1] Demo 默认 240px 把核心已选列表压进滚动区

**为什么重要**：设计标本和 API 默认值都以 380px 为主要核对空间，但文档初始示例选择 240px。1440px 下右侧首屏只有两条，390px 下只有三条，且马上出现“下方还有”提示。开发者第一次打开文档会先看到被压缩的批量栏和不完整的已选清单，难以判断标准布局是否满足业务核对目标。

**修复建议**：把 Demo 初始 `panelHeight` 改为 380px，把 240px 保留为显式的“紧凑/窄屏压力测试”选项；或者在标题旁明确标注“当前为紧凑压力测试”，并在首屏同时提供标准高度截图。保持窄屏最低 352px 的触控契约。

**建议命令**：`/impeccable adapt`

### [P2] 批量动作、计数和禁用原因的层级在窄中栏里互相竞争

**为什么重要**：在 240px 桌面和 320/390px 移动布局中，一个动作同时展示图标、动作名、可加入/已选计数和上限原因。上限原因仍是长句，导致中栏显得像状态说明区，主动作的优先级不明显；用户需要先读多行小字才能理解按钮为什么不可用。

**修复建议**：保留按钮 + 一行短计数作为主层级，把完整上限原因放到同一动作的 tooltip/可展开说明或统一状态行；启用状态只保留动作名和计数，禁用状态再追加一句原因。移动端可把两个动作各自变成“图标 + 动作名/计数”两行，并让原因横跨整行但不挤压按钮。

**建议命令**：`/impeccable clarify`

### [P2] 桌面长名称只有 chevron，缺少可见的“查看全文”入口

**为什么重要**：380px 桌面截图中的未加载长名称确实可展开，键盘和 aria-label 也有说明，但视觉上只看到一个小箭头；不使用鼠标悬停或辅助技术的用户很难知道它是可操作的。移动端在 420px 以下显示“查看全文”，桌面反而失去这个识别线索。

**修复建议**：桌面截断项在名称末尾显示小号“查看全文”或为 chevron 提供稳定 tooltip；展开后保留“收起”文案。文本应使用与状态标签相同的次级层级，避免破坏 32px 短名称密度。

**建议命令**：`/impeccable clarify`

### [P2] VirtualTree Demo 的渐进披露入口不够可发现

**为什么重要**：`<details>` 默认收起确实减少了首屏噪音，但 `.virtual-tree-demo__controls summary` 和嵌套摘要使用 `display: flex` 后，浏览器 disclosure marker 在文档渲染中几乎不可见。读者只看到“演示状态和更多操作”文字，不一定知道还有筛选、定位、父子勾选、主题和插槽压力测试。

**修复建议**：给每个 summary 加明确的 LxIcon chevron（同步 `aria-expanded`、旋转和减少动效），并在主摘要后显示简短数量提示，如“4 个状态 · 2 组高级操作”。保留默认收起，让入口本身承担发现性。

**建议命令**：`/impeccable onboard`

## Persona Red Flags

### Alex（熟练管理员）

- 键盘树操作、筛选批量和全量加入/移除满足快速路径；移除后焦点能移到下一项，表现良好。
- 首屏默认 240px 迫使 Alex 先切换到 380px 才能核对完整已选清单，增加了不必要的一步。
- 打开 Demo 设置后要在 4 个状态、3 个参数和高度之间辨认目标，状态验证路径变长；组件没有独立的面板切换快捷键。

### Sam（键盘/屏幕阅读器用户）

- tree/treeitem 的层级、展开、勾选和 `aria-describedby` 信息完整，键盘 `ArrowDown` 与 `Space` 实测有效；移除按钮按 Enter 后焦点恢复到下一项。
- 已选列表容器本身可聚焦并播报“当前显示/总数”，但没有专门的键盘滚动提示；长列表中需要依赖浏览器默认滚动行为寻找隐藏项。
- 桌面长名称的可展开入口有 `aria-label`，但可视 chevron 没有文字，低视力且不使用屏幕阅读器的用户仍可能错过入口。

### Casey（单手窄屏用户）

- 390px/320px 下切换按钮和移除按钮达到触控尺寸，页面没有横向溢出，长名称可两行折叠并进入“查看全文”。
- 240px 示例在窄屏实际变为 352px，但首屏仍只显示三条；第四条和未加载说明需要滚动，返回页面后需要再次定位“已选”分段。
- 批量操作位于面板之间而非底部拇指区，且禁用原因会占据额外一行；在中断后回到页面时，用户需要重新阅读动作状态。

## Minor Observations

- Demo 的 `HUD 深色主题`只改变预览区域，外层状态/说明仍为浅色；文档已明确这是比较基准，建议继续在截图说明中标出作用范围。
- 设计标本的中栏只显示图标，而当前版本增加动作名与计数；这提升无障碍识别，但需要通过更清晰的主次层级避免变成第三个信息面板。
- TransferPanel 右侧过滤框和已选列表均有清除/空结果文案；VirtualTree Demo 的错误状态有“重试”，状态反馈覆盖较完整。
- 320px 下面板内容保持在可用宽度内，但文档站自身的外边距使实际组件内容宽度约 257px；建议在文档截图说明中注明这是文档壳层的可用宽度，不代表业务页面容器宽度。

## Questions to Consider

- 文档首屏要表达“标准 380px 的推荐用法”，还是要优先展示“240px 紧凑压力测试”？两者是否应拆成默认示例与独立边界示例？
- 批量加入达到上限时，用户最需要看到的是“剩余名额”、 “需要加入多少项”，还是一个可直接执行的“按剩余名额加入”动作？
- 桌面长名称是否应与移动端统一显示“查看全文”，让相同的可展开模式在所有宽度下都可被看见？

## A 结论

这是一个有明确产品语境、状态与可访问性基础的组件实现。设计质量主要被文档 Demo 的默认紧凑高度和两处渐进披露线索拖低；先修正默认展示基准、批量操作层级和桌面全文入口，再做下一轮 Critique，能够直接改善首次理解与移动端核对效率。
