## 认知负荷

- 单一焦点：通过。每个 Demo 都有明确的组件任务。
- 信息分组：通过。表单、抽屉键值行、空态动作和 Banner 说明均分组清晰。
- 相关信息视觉归组：通过。portal、内容、footer 边界稳定。
- 视觉层级：通过。主标题、主操作、错误和状态文字可区分。
- 一次处理一个决定：通过。重试、关闭和危险确认均按单步决策组织。
- 最小选择：**失败 1 项**。PageCard 同时显示加载、边框、内边距、错误和 HUD 五个开关，超过四项的工作记忆建议。
- 工作记忆：通过。当前任务所需数据留在当前容器内。
- 渐进披露：通过。代码和 API 细节仍由文档结构分段承载。

判定：**低到中等负荷，8 项中 1 项失败**。该失败属于 Demo 观测面板的组织问题，不阻断业务组件使用。

## 情绪旅程

1. **进入：可信。** HUD 浮层不再闪回白卡，组件与页面一开始就处在同一视觉语境。
2. **操作：稳定。** Drawer 内容、footer 和关闭按钮在桌面/375px 都可达，Escape 给熟练用户一条直接退出路径。
3. **阻断：可理解。** Dialog 错误持续贴近地点字段，焦点直接落到首个错误，读屏关系也明确。
4. **恢复：有把握。** PageCard 点击刷新先给忙碌反馈，再回到成功数据；用户不需要手动猜测错误是否清除。
5. **结束：清晰。** 空态保留下一步动作，Banner 告诉用户受影响字段入口，危险抽屉仍要求明确确认。

## 强项

1. **Portal 主题闭环。** Dialog 与 Drawer 在真实 `append-to-body` 结构下都继承 HUD 令牌，避免局部主题与浮层主题分裂。
2. **键盘与错误恢复形成可验证行为。** Drawer Escape 实际关闭；Dialog 首错聚焦和字段关联实际可见；PageCard retry 从错误经 loading 回到数据。
3. **移动边界被约束在组件自身。** 抽屉铺满视口但不扩张页面，PageCard API 表在自身表格内横向滚动，空态和 Banner 保持可读。

## 优先问题

### [P2] PageCard Demo 仍同时暴露五个状态开关

这不会影响业务组件，但会让首次阅读者把 Demo 当配置面板。可把边框、内边距和 HUD 收入“显示选项”折叠组，默认只保留加载与错误两个核心状态。

### [P2] 移动 API 表的横向滚动发现性仍可加强

表格自身已经 `overflow-x: auto`，页面没有横向溢出，解决了可用性风险；但窄屏用户只看到前三列，需要轻量的“左右滑动查看说明”提示或在表头旁提供可见滚动线索。

### [P3] 辅助文字保持紧凑密度

Drawer 的标签/提示和 ErrorBanner 的辅助说明以 11–12px 呈现，当前对比度和语义足够，但长时间审计或低视力用户可能更适合 13px 及以上的阅读尺寸。应在令牌层统一调整，避免业务页各自放大。
