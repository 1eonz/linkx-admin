# ColForm 设计评审

目标：协同岗新增/修改表单，Operate 模式

目标源码：other-admin/admin-vue3/src/views/collaboration/components/ColForm.vue

浏览器目标：http://127.0.0.1:30847/collaboration/index

## 设计特异性判断

这是一套符合 LinkX admin 明亮表面、蓝色主按钮、Element Plus 表单惯例的后台 CRUD 表单，视觉一致、层级可扫描，但表单骨架本身可无改动地出现在多数企业管理系统中，产品辨识度偏弱。业务特异性主要来自“协同岗类型”“归属组织”“关联人员”等字段、组织树选择，以及已被其他协同岗绑定的人员禁用规则。对 Operate 场景而言，清楚可靠比强装饰更重要；现有方向合适，但“警务业务协同”特色还只落在文案和规则中，没有转化成更清晰的关联关系说明。

## 总体印象

桌面新增与编辑都简洁、宽松，手机编辑也能容纳完整字段和已选人员。最值得处理的是窄屏人员下拉遮挡底部动作，以及键盘焦点对上传控件的重复停留；其次是人员空态可能错误归因到组织本身。

## 认知负荷

Checklist（依据新增与编辑表单的可见内容）：

- [x] 单一焦点：弹窗聚焦一项表单任务，背景被遮罩。
- [ ] 信息分块：普通协同岗表单约有六个字段，但没有明确的小节；用户须逐行扫过一整列。
- [x] 相关分组：组织与关联人员相邻，更新表单的锁定类型提示紧贴类型控件。
- [x] 视觉层级：弹窗标题、字段标签和底部确定按钮容易辨认。
- [x] 一次处理一项：标准纵向表单将输入分开。
- [x] 选择数量适中：本次可见类型为 2 项，编辑人员为 3 项，未超过 4 项。
- [x] 工作记忆：所选姓名、组织、人数和锁定原因都留在弹窗内。
- [x] 渐进呈现：警单类型字段依类型出现；人员选项须先确定组织。

失败项 1 项，整体负荷低。字段分组可作为后续优化，不足以单独阻塞发布。

## 情绪历程

打开新增弹窗时，明确字段标签与字符计数让人容易起步。选组织之后，若列表显示“当前组织暂无可关联人员”，用户可能困惑或担心组织配置有误，尤其是同一 Mock 组织在另一岗位类型编辑态显示出 3 人。修改已有记录时，已选人员和“共 3 人、已选 2 人”提供了安心感，锁定类型也给出明确原因。保存后的成功峰值来自源码中的成功提示与关闭弹窗行为，但本轮为避免写入，没有触发或观察真实提交结果；此处属于源码推断。

## 做得好的地方

1. 编辑态把协同岗类型禁用，并在控件下方解释创建后不可修改，原因与限制在同一视线内。
2. 关联人员直接显示已选姓名、总数与已选数；已绑定至其他协同岗的人同时禁用并显示原因，避免用户靠颜色猜规则。
3. 人员请求错误保留已选值并提供重试入口；源码还处理过期查询取消，能降低切换组织/搜索时旧结果覆盖的风险。

## 优先问题

### [P2] 手机人员列表遮挡弹窗底部操作

**影响：** 375×812 的编辑态人员下拉有 3 个选项，弹层向下展开至弹窗底部，覆盖取消和确定按钮所在区域。用户要先收起下拉才能安全离开或继续确认，操作区在最需要时暂时不可见。

**建议：** 小视口下让下拉改为向上展开，或将候选列表限制在对话框可用高度内并保证页脚可见。复验 375×812 及更短视口。

**建议命令：** /impeccable adapt

**证据类型：** 浏览器直接观察，手机编辑态，375×812。

### [P2] 上传控件在 Tab 顺序中重复出现

**影响：** 编辑态从名称输入框按 Tab 到达“点击上传”后，再按一次 Tab，视觉仍停留在同一个“点击上传”按钮；AX 树也把上传区域暴露为嵌套的两个同名 button。键盘用户会误以为第二次按键没有移动，延长表单导航。

**建议：** 保留一个可聚焦的上传触发元素，检查 el-upload 包装与内部 el-button 的语义，确保 Tab 只经过一次，并验证焦点可见和 Enter/Space 可用。

**建议命令：** /impeccable audit

**证据类型：** 浏览器键盘操作与 AX 树观察；未使用屏幕阅读器验证实际朗读。

### [P2] 人员空态可能把筛选结果误说成组织无人

**影响：** 新增时选择“普通协同岗”和“市局指挥中心”，可见状态是“当前组织暂无可关联人员”。同一组织的“人员核查协同岗”编辑态却显示共 3 人。源码显示查询可在全局开关开启时携带岗位类型，因此零结果可能表示“当前岗位类型下没有可关联人员”，不一定是组织没有人员。现有措辞会让用户怀疑组织选择或人员配置。

**建议：** 明确描述筛选范围，如“当前协同岗类型下暂无可关联人员”；若系统允许通过变更岗位类型解决，应在允许变更时给出清楚的下一步。用含零人、仅其他类型有人和请求失败的 Mock 分别复验文案。

**建议命令：** /impeccable clarify

**证据类型：** “普通协同岗”零结果与“人员核查协同岗”三人的浏览器观察；岗位类型作为查询参数的条件逻辑属于源码推断，具体后端筛选语义未联调。

## Persona 红旗

**Alex，熟练操作员：** 可用 Tab 依序访问名称、上传、组织、已选标签、人员选择与页脚操作；但上传按钮占两个连续焦点位，没有观察到表单级快捷键。快速操作会被一次多余停留打断。

**Jordan，首次使用者：** “协同岗名称”“归属组织”容易理解，上传限制也清楚；但普通协同岗零人状态没有说明与岗位类型的关系，可能让 Jordan 重选组织或怀疑数据缺失。“警单类型”也没有说明选择它的业务后果。

**Sam，键盘/读屏用户：** 表单控件有标签，人员加载状态使用 status/live 区域，已绑定人员带文本原因；两次连续上传焦点是已复现的键盘摩擦。仅查看浏览器 AX 树，未运行 NVDA/VoiceOver，不能据此宣称读屏验收通过。

## 次要观察

- 1280×720 下新增对话框宽 600 px 并居中，字段和底部操作不拥挤；编辑对话框高度随警单类型字段变化。
- 375×812 下表单宽 343 px，左右留边 16 px，字段改为标签在上；本轮读取的 body scrollWidth 为 375 px，没有页面横向溢出。
- 编辑态选人弹层中，被禁用的人仍有具体文字理由；较低对比度是辅助信息，建议继续保证足够可读。
- 关闭或取消编辑会放弃尚未提交的修改。本次未输入业务内容，未判断是否需要脏数据拦截。

## 追问

- “当前组织暂无可关联人员”是否代表组织确实没有成员，还是代表该岗位类型下没有符合条件的人？用户应如何知道差别？
- 在手机上打开人员候选项时，是否必须同时看得到弹窗的取消和确定操作？
- 上传图标是创建/修改岗位的常用步骤吗？如果常用，能否让键盘一次到达，并在选择后更清楚地呈现预览和替换状态？
