## 设计特异性判定

**判定：中等特异性（可复用的 LinkX 检索模式，有明确业务密度取向，但仍接近通用后台筛选器）。**

组件具备 24 列字段栅格、超过 8 个字段时的首 4 项折叠、受控 `modelValue`、宿主注入 `meta/controls/filters` 插槽及中文政务字段语义，能表达高密度列表页检索的使用场景（`index.vue:69-78,316-367`；Demo 字段模型 `basic.vue:11-87`）。面板卡片、顶部标签、主次按钮、Element Plus 风格控件与通用 token 组合也很稳健，迁移到任意 CRM、工单或数据后台几乎无需改造。设计稿的警务身份主要落在文案、状态元数据和色彩（`code.html:116-131,236-249,502-510`），没有形成组件级的专属信息结构。因此它有明确的“紧凑中台检索”定位，但还不能单靠视觉被识别为 LinkX/警务工作台的独特表面。

## 总体印象

这是一个结构清楚、密度控制意识较好的列表检索容器。默认字段标签和控件之间的关系明确，搜索是唯一主操作，`loading`、`canReset`、受控折叠和插槽让页面宿主可以保持请求与业务状态边界。Demo 同时演示成功、空结果和失败，文档也记录了键盘与窄屏验收，这些都提高了可落地性。

最大风险集中在“用户看不见的状态”：折叠会从 DOM 中移除后续字段，但不提示隐藏数量或已激活条件；Esc 是无确认的全局重置；设计稿承诺的 field-level error 与代码类型缺口明显。再加上设计稿、文档、运行时事件契约不一致，组件在多个业务页复用后容易出现不同团队各自猜测的行为。

### Working-memory decision points

- 默认折叠：4 个可见字段 + 查询 + 重置 + 展开，共 7 个可感知对象，已接近上限。
- 展开态：Demo 中 10 个字段 + 查询/重置/收起，至少 13 个对象；应按“高频基础、更多条件、状态/结果”分组或提供摘要。
- 单个 select 的候选项在 Demo 为 2–3 个，单控件可接受；风险来自字段数量和不可见条件，而不是单个菜单长度。

## 情绪旅程（Peak-end）

1. **进入**：标签、占位文本、卡片结构带来“可以直接开始”的低摩擦感；32px 紧凑密度符合中台用户预期。
2. **填入**：控件变更即时回写受控对象，Enter 查询快捷；但 field-level 校验缺失，异常值直到请求失败才有反馈。
3. **展开/收起**：展开可以继续深挖条件，属于效率峰值；收起时隐藏条件不计数，若结果变少，用户容易怀疑系统是否丢失筛选。
4. **查询**：loading 按钮防重复提交，Demo 的状态文字提供确认；真实宿主若不注入 `meta`，组件不会自己说明查询中/结果数/失败。
5. **空结果/失败**：空结果只有“暂无匹配结果”，失败只有错误文本，缺少“清除某条件/重试/查看已应用筛选”这类恢复动作，情绪低谷拉长。
6. **结束**：成功时“查询到 N 条”是清晰但偏弱的正反馈；重置或 Esc 后没有撤销，误清空会成为负向结尾。

## 主要优点

1. **业务编排边界清晰**：组件只负责字段展示、模型更新、折叠和动作事件，列表请求由宿主注入；`meta` 与 `controls` 插槽让结果语义不被组件库硬编码（`index.vue:41-58,321-367`）。
2. **高密度场景已有渐进披露骨架**：24 列栅格、前 4 项默认可见、移动端单列和 footer 重排兼顾桌面密度与窄屏可读性（`index.vue:384-501`）。
3. **状态与键盘路径有可验证示例**：Demo 覆盖成功/空结果/失败、loading、Enter/Esc、结果数量和受控折叠，文档也把这些行为写出（`basic.vue:93-169`；`lxsearchbar.md:35-43`）。

## 优先问题

### P1 — 折叠隐藏条件没有可见性或活动摘要

- **证据**：`canCollapse` 仅以 `fields.length > 8` 决定，`visibleFields` 只保留前 4 项（`index.vue:69-78`）；footer 只有“展开/收起”和箭头（`index.vue:325-339`）。设计稿明确给出“已折叠隐藏 4 个深度研判维度”的 badge（`code.html:381-390`），但组件没有对应能力。
- **影响**：用户看不到隐藏字段数量，也不知道隐藏字段是否仍有非默认值；在查询结果变化时无法判断是条件导致还是系统丢失条件。对强依赖准确筛选的警务/运营列表属于主要信任风险。
- **建议**：在折叠按钮旁显示隐藏字段数和激活数；当隐藏字段有值时显示“已应用 N 个隐藏条件”，点击后聚焦第一个激活字段；展开后保持当前焦点并给出分组标题。

### P1 — 运行时、正式文档和设计 API 的契约漂移

- **证据**：运行时 `search` emit 无参数（`index.vue:34-38,196-198`），设计 API 表写 `(query) => void`（`code.html:747-750`）；设计表写字段超过 4 个折叠（`code.html:735-744`），运行时实际为超过 8 个，正式文档为超过 8 个（`lxsearchbar.md:21-23`）。
- **影响**：接入者会按不同来源实现不同监听器和布局预期，形成查询参数重复抓取、折叠阈值分歧和难以复用的示例。组件库的“可预测性”被破坏。
- **建议**：确定唯一契约（建议保持 `modelValue` 受控、`search` 无 payload 或明确传出快照二选一），同步 `types.ts`、Demo、文档和设计 HTML；统一“超过 8 个”及“首 4 项”的说明，并为事件写实际类型签名。

### P1 — 设计稿承诺的 field-level error 没有组件契约

- **证据**：设计稿展示错误边框、错误图标及“警号格式不匹配”的行间说明（`code.html:476-498`）；`LxSearchFieldBase` 只有 placeholder/default/span/clearable/disabled，没有 `error`, `invalid`, `help` 或 `aria-describedby`（`types.ts:22-30`）；模板也没有错误分支（`index.vue:223-313`）。
- **影响**：真实页面无法在字段附近解释格式错误或给出修复提示，只能在 meta 或全局 toast 反馈；用户需要猜是哪一个字段阻止查询，尤其在多个条件组合时。
- **建议**：为 schema 增加可受控的 `invalid`/`error`/`describedBy`（或明确由宿主 slot 承担），把错误关联到控件 `aria-invalid` 和描述节点；Demo 至少演示一项校验失败后的修复路径。

### P2 — Esc 是无确认的全局重置，缺少撤销路径

- **证据**：section 监听 `@keyup.esc="reset"`（`index.vue:215-222`）；`reset()` 会清空模型并立即触发 `search`（`index.vue:200-206`）。Demo 把该行为写为“Esc 重置”（`basic.vue:164-166`），设计稿也公开宣传同一快捷键（`code.html:248-249`）。
- **影响**：用户本来想关闭下拉/日期面板或退出焦点状态时，可能意外丢失多项筛选并发起新查询；没有 toast、Undo 或恢复上一次查询条件。
- **建议**：仅在文本输入聚焦且字段确实有改动时启用 Esc 清空，或将 Esc 默认留给控件关闭，把“重置全部”改成明确快捷键/确认；至少提供一次性撤销上次重置。

### P2 — 窄屏可触达性、语义状态和动效降级不足

- **证据**：标准控件高度为 32px（`variables.css:136-138`），折叠按钮最小高度直接复用 32px（`index.vue:445-450`）；移动端只是单列和纵向 footer（`index.vue:476-501`）。组件只有 `section aria-label`，没有 `role="search"`/`aria-busy`，字段错误没有 ARIA 关系；chevron 使用过渡但没有 `prefers-reduced-motion` 分支（`index.vue:468-473`）。
- **影响**：单手移动用户的 32px 触控目标偏小；屏幕阅读器用户不能稳定知道查询进行中/失败及隐藏条件状态；减少动效偏好用户仍会看到旋转过渡。
- **建议**：保留视觉 32px 时为移动端增加 44px hit area（或外层 padding）；将面板标为 `role="search"`，绑定 `aria-busy` 和结果状态；补充 `aria-invalid`/描述关联及 `prefers-reduced-motion: reduce`。

## Persona 红旗

### Alex（不耐烦的熟练用户）

- Enter 查询和 Esc 重置能加速常用路径（`basic.vue:164-166`）。
- 展开/收起没有键盘快捷键或隐藏条件计数；Alex 需要用鼠标猜测是否还有字段。
- Esc 直接重置并立即请求，批量填十个条件后误触会造成高成本返工；没有保存/恢复最近查询或批量清空策略。

### Sam（键盘/屏幕阅读器用户）

- label 与控件 ID 的基本关联存在（`index.vue:229-235`），折叠按钮有 `aria-expanded`（`index.vue:327-331`）。
- 搜索容器是带 label 的普通 `section`，没有 `role="search"` 或 `aria-busy`；失败/空结果依赖宿主是否提供 `role=status`，组件本身无法保证公告。
- 隐藏字段从 DOM 中消失且没有“隐藏条件仍有值”的公告；设计稿的错误状态没有 `aria-invalid`、`aria-describedby` 入口。
- 以非字母数字替换 key 生成 ID（`index.vue:100-102`）可能令 `a.b` 与 `a-b` 产生相同 ID，造成错误 label 关联，需在 schema 约束或 ID 生成策略中处理。

### Riley（边界压力测试者）

- 空结果与网络失败的演示路径存在，但真实组件没有重试、字段级定位或保留上次结果的契约（`basic.vue:107-119`）。
- `LxSearchField` 未提供未知类型的 fallback；传入未支持 `type` 时会渲染 label 但没有控件（`index.vue:233-313`），容易形成“看起来可筛选、实际被忽略”的静默失败。
- 超长 label/placeholder、动态切换 fields、重复或规范化后冲突的 key 均没有可见诊断；用户可能得到空白或错联动字段。

### Casey（分心的移动用户）

- 移动端字段转单列，动作区占满宽度，方向正确（`index.vue:476-501`）。
- 32px 输入/折叠命中区和顶部字段顺序不符合 44px 触控与拇指区习惯；查询/重置不固定在底部，长表单中断后回到顶部成本高。
- 没有中断后恢复或已应用条件摘要；切换应用再回来时，用户难以确认隐藏字段是否仍生效。

## 次要观察

- Demo 的“成功/空结果/失败”按钮和面板内 meta 状态重复展示状态；作为示例有助于验收，但若照搬到业务页会引入两个状态来源（`basic.vue:127-166`）。
- Demo 所有字段显式 `span: 8`，桌面为三列；设计稿标准形态是四列且文档称默认字段占 6 列（`basic.vue:11-87`；`code.html:153-235`；`lxsearchbar.md:47-49`）。示例应说明这是演示可配置 span，而不是标准布局。
- `filters` 插槽以 `display: contents` 插入 24 列网格，没有公开 slot item 的 span/label/错误语义约定，定制字段可能破坏布局与可访问性（`index.vue:316-319,425-427`）。
- `LxSearchField` 的 `options` 对非 cascader 类型也允许 children，类型层没有禁止无效组合（`types.ts:32-40`）；这会增加接入者对树数据契约的猜测。
- 用户给定的组件内文档路径不存在，实际文档在 `linkx-fe/docs/components/lxsearchbar.md`；设计参考中的 API 表仍保留旧的 `Record<string, any>` 表述，而运行时类型已收紧为 `Record<string, unknown>`（`code.html:729-732`；`types.ts:42-50`）。

## 建议优先级与验证问题
