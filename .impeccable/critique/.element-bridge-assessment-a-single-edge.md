# Assessment A：Element Bridge 独立视觉评审

评审目标：`http://127.0.0.1:4174/components/element-bridge.html`

方法：使用新建浏览器标签进行独立视觉与交互检查；未运行静态 detector，未读取 Assessment B。页面模式为 Operate（组件文档中的可交互验收面板）。

## 设计特异性

**判断：中等偏强，能看出这是 LinkX 组件库的桥接验收页，但展示面板本身仍较通用。**

“基础控件交互示例”不是抽象截图，而是把 LinkX 按钮/表单控件规范、Element Plus 原生契约、HUD 深色主题、通知渠道三态、标签折叠、多主题焦点与错误恢复放进一个可操作的本地例子中。中文标签、LinkX 主色、明确的 `lx-ui/style.css` 接入信息和 Vue3 依赖边界都与本库相关，使页面不是任意产品都能直接替换名称的通用表单。

外围仍是熟悉的 VitePress 组件文档结构，演示面板是常规边框容器；它们没有进一步强化 LinkX 的视觉个性。不过对供开发者核对行为的文档页而言，克制的壳层是合适的，组件表现和可复现状态优先于品牌装饰。

## 视觉与交互证据

- 桌面观察尺寸约 1265×720。分别查看了浅色与 HUD 深色主题下“协同部门”多选控件的关闭焦点态。
- 375×812 移动视口分别查看了浅色与 HUD 下的多选关闭焦点态。文档宽度为 375 CSS px，未出现页面横向溢出；正文宽 327px，多选控件为 301×32px。
- 四种主题/视口组合中的多选控件均表现为沿控件边界的一圈蓝色焦点线。截图中没有看见原先“控件内线 + 外侧光晕”分离成双轮廓的现象。当前聚焦规则视觉上稳定，标签折叠为“指挥中心 +1”时控件尺寸没有明显跳动；Escape 关闭弹层后焦点仍回到多选控件。
- 浏览器计算样式佐证当前控件使用 2px 内描边式阴影，外层 `.el-select` 没有附加阴影；这是页面渲染状态的观察证据，不是源码 detector 结果。
- 触发必填校验后，“请输入任务名称”“请选择责任部门”与表单提示均可见。手动聚焦错误的责任部门下拉并关闭弹层后，能看到单一红色 2px 内描边，没有与蓝色焦点圈叠加；错误文字仍可见。
- 复位操作给出“已重置”反馈。没有观察到控件宽高因焦点或主题切换而变化。

**对当前问题的结论：在本轮可视检查的浅色/HUD、桌面/375px 状态里，多选外圈的双层轮廓已解决。** 后续合并评审仍应按计划复验实际浏览器截图；此结论只覆盖上述控件和状态。

## 认知负荷

结论：**低负荷，1 项清单失败。**

- 单一焦点：通过。页面标题、用途说明和组件示例形成清楚的阅读入口。
- 分块：通过。按钮、主题、表单字段、操作按钮、页签和接入说明分别成组。
- 分组：通过。相关的全选项与复选子项在示例中分行缩进；输入字段有明确标签。
- 视觉层级：通过。页面标题高于示例和接入说明，表单标签及必填状态清楚。
- 一次一项：通过。主要交互逐项展开；选择弹层不会强迫同时完成多个决定。
- 最少选择：**失败。** 按钮演示一次展示六个同类外观选项，窄内容区会让最后的禁用态落到单独一行；这是组件比较页有意展示覆盖面的结果，但视觉上容易被理解为一组并列命令。
- 工作记忆：通过。复位与错误说明在当前示例中可见，不要求记住前页内容。
- 渐进披露：通过。较长示例代码折叠收起，用户可按需要展开。

失败项只有一项；按钮选择是展示用而非业务决策，因此不构成高负荷问题。表单本身的按钮操作为“校验表单”和“重置”两项，负担可控。

## 情绪旅程

用户从组件总览找到桥接页后，标题和简短说明会建立这是样式与行为验收面板的预期。进入表单后，多种状态都能直接尝试，主题和焦点变化能被确认。触发错误时，红色字段边线与贴近控件的提示提供了明确诊断；但焦点停留在校验按钮上形成一次轻微挫折，尤其是仅用键盘的用户需要再导航回字段。点击“重置”后看到确认文字，恢复感明确。峰值是可复现的控件状态与可见反馈，结尾反馈令人安心；焦点跳转可让错误恢复更顺畅。

## 做得好的地方

1. **焦点边线有真实边界感。** 多选关闭焦点态在两种主题、桌面与 375px 中均贴合控件边界；标签折叠没有把轮廓拉成两圈或造成明显尺寸跳动。
2. **样例覆盖的状态有上下文。** 责任部门必填错误、通知渠道全选三态、深色主题和多选标签折叠都能在同一面板中操作，不需要模拟后端数据。
3. **接入边界对开发者清楚。** 页面说明原生 Element Plus 控件可从 `lx-ui` 导出，也解释了表单校验仍由 Element Plus 处理，减少组件库用户对责任归属的猜测。

## 优先问题

1. **[P2] 校验后没有把键盘焦点带到首个错误字段。** 点击“校验表单”后错误提示出现，但焦点仍在按钮。用户可以通过红色定位，但键盘用户必须手动向前导航，修复路径不够直接。建议验证失败时聚焦首个无效控件；若不适合自动移动，则提供带字段链接的错误摘要。建议使用 `/impeccable harden`。
2. **[P3] 按钮变体组在桌面内容宽度下孤立换行。** “禁用操作”落在第二行，视觉上像意外断行而非六态比较。将变体组织为紧凑网格或为样例组明确换行节奏，并让小屏保持整齐。建议使用 `/impeccable layout`。
3. **[P3] 首屏说明与后续接入说明承担了较多技术上下文。** Element Plus 契约、设计目录、动态表单和依赖移除说明都重要，但在 375px 上需要较多纵向阅读才能回到表单示例。将状态操作说明留在演示附近，把迁移背景收在接入/边界小节，能更快进入示例。建议使用 `/impeccable distill`。

## Persona 红旗

- **Alex（熟练管理员/开发者）**：能直接聚焦多选、查看已选标签并用 Escape 关闭弹层；键盘闭环明确。校验失败后需要自己从按钮移至字段，缺少首错快捷定位。示例未证明是否有批量快捷路径，但本页不是批量业务页，暂不视为阻断。
- **Sam（键盘与辅助技术用户）**：字段及复选框在可访问性树中有名称，焦点边线在浅色和 HUD 背景上可见。校验后焦点留在按钮是明确的效率红旗；本评审未使用真实屏幕阅读器，不能确认校验提示是否作为实时公告播报。
- **Casey（移动端用户）**：375px 下页面无横向溢出，多选控件宽度稳定，标签折叠可用。面板包含大量控件，用户需纵向滚动；这符合组件覆盖示例的目标，但不适合把它当作短任务流程来衡量。

## 次要观察

- HUD 深色主题的面板与控件文字仍可辨认，复选框选中态与标签没有和背景融在一起。
- 样例控件覆盖很多类型，纵向高度偏长；折叠代码示例控制了文档本身的额外长度。
- 本轮没有检验浏览器 200% 缩放、真实 NVDA/VoiceOver 宣读或减少动效设置；这些不影响已观测的多选外圈结论。

## 值得追问的问题

- 校验失败时，开发者期望页面自动聚焦首错字段，还是更偏好一个可逐项跳转的错误摘要？
- 按钮变体需要作为同一组可操作命令展示，还是明确呈现为只用于比较外观的状态矩阵？
- 首屏是否应更明确地区分“可交互验收”与“迁移接入说明”，让第一次打开组件页的人更快进入操作区？
