## 设计特异性结论

**LLM 评估：基本具备 LinkX 管理台的专属性，但仍有两处类别化。** SearchBar 的 24 列栅格、32px 控件、状态/快捷键带和超过 8 项折叠体现了该组件库的密度规范；StatusSwitch 的 `0/1` 兼容、权限降级和关闭确认也明显来自现有业务。组件视觉仍较通用：字段级图标/辅助信息没有进入配置契约，StatusSwitch 的确认内容只有通用标题和一段消息，未达到设计稿中“核心节点、影响范围、审计写入”的高风险语境。

本次没有读取或引用 Assessment B、detector 或代码审查输出；因此本节没有自动扫描结论，也不把 detector 当作视觉证据。

**浏览器证据：**使用独立上下文访问 `http://127.0.0.1:4177/components/lxsearchbar` 与 `/components/lxstatusswitch`，视口为 1440×1000 和 375×900，保存于本目录 `screenshots/`。两页 375px 均为 `scrollWidth=clientWidth=375`，未发现页面级横向溢出。SearchBar 11 字段 Demo 初始展示前四项，第四项日期字段按 Demo 的 span/网格落到下一行；代码中 `fields.length === 4` 的同一行操作分支没有在文档 Demo 中直接呈现。StatusSwitch 关闭确认层在浏览器中可见；桌面视觉轨道为约 42×20，外层命中高度约 32，375px 外层命中区域为 44×44。

## 总体印象

这是一次有效的组件级修复：状态反馈、折叠、loading、权限降级和确认拦截都能在 Demo 中理解。最大机会是把设计稿里“高风险业务操作”的上下文真正带进组件契约，并让表格行名称在只读/加载/无权限状态下也完整到达读屏用户。

## 做得好的地方

1. SearchBar 的默认前四项折叠和 `hiddenFieldCount` 文案让复杂筛选先保持可扫描；四字段同行操作写成明确分支，移动端回落为全宽 44px 操作区。
2. SearchBar 用 `role="search"`、`aria-busy`、状态 live region 和 Enter/Esc，查询等待、空结果和失败后的反馈路径完整。
3. StatusSwitch 把旧业务 `0/1`、loading 锁、权限不足 LxTag 和关闭确认集中在一个小契约中；设计稿要求的中性灰关闭态和绿色开启态得到保持，移动端命中区域也达到 44px。

## 优先问题

### [P1] 高风险确认层缺少设计稿要求的业务影响上下文

**为什么重要：**设计稿的 HUD 确认层明确展示“核心节点”“跨域调度中断”“受影响单位/警力”“不可篡改审计日志”。当前 Demo 只呈现“确认停用该节点？”和一行说明；浏览器截图虽有遮罩、取消和危险按钮，但用户无法从组件层获得同等风险判断。

**修复：**允许确认配置提供影响摘要、目标实体、风险等级/审计提示等结构化插槽或字段，并在 Demo 展示设计稿的完整高风险文案；保留宿主可自定义而不把业务 API 放入 lx-ui。

**建议命令：**`/impeccable clarify`

### [P1] 只读、loading、无权限状态没有稳定的表格行名关联

**为什么重要：**Demo 只为布控、旧值和确认行传 `aria-labelledby`；loading、disabled、permission 行没有业务行名。组件把 ARIA 关联属性传给实际 LxSwitch，但降级为 LxTag 时只设置了通用 `aria-label`，读屏用户可能只能听到“禁用/只读”，不知道是哪一行。

**修复：**为 fallback Tag、loading 和 disabled 展示保留 `aria-labelledby`/`aria-describedby` 的行级关联，或提供明确的 `label`/`statusLabel` 契约；Demo 为每个状态行补唯一行名并实际验证读屏顺序。

**建议命令：**`/impeccable harden`

### [P2] 四字段同行的关键设计态没有可视 Demo 对照

**为什么重要：**设计稿的核心示例是四字段同一行、操作组底对齐；当前 SearchBar Demo 使用 11 字段，截图看到的是前 3 项一行、日期落下一行的折叠态。虽然源码有 `fields.length === 4` 分支，文档读者仍无法直接确认该拍板布局。

**修复：**在 SearchBar Demo 增加一个恰好四字段的标准态，明确显示四字段同行、查询/重置底对齐，并保留现有多字段折叠态作为第二示例；同时在 375px 展示回落后的单列顺序。

**建议命令：**`/impeccable layout`

### [P2] 默认反馈在 Demo 中重复且缺少设计稿的命中信息层次

**为什么重要：**SearchBar Demo 顶部工具栏显示一次“等待查询”，组件 meta 插槽又显示一次；初始状态重复占据注意力，而设计稿的状态带把命中数、延迟、筛选指纹和快捷键分层组织。重复反馈会削弱用户对真正结果状态的关注。

**修复：**保留一处宿主模拟控制状态，把组件 meta 专注于结果/延迟/快捷键；成功、空结果、失败分别使用同一位置更新，避免默认状态与 Demo 状态重复。

**建议命令：**`/impeccable distill`

### [P3] 字段级图标和辅助说明无法由 SearchBar schema 表达

**为什么重要：**设计稿给关键字、组织树、日期和状态字段配了图标或字典/格式辅助信息；当前 schema 只有 label、placeholder、options，组件因此更像通用表单网格，产品识别度弱于参考标本。

**修复：**在不强耦合业务的前提下增加可选前缀图标和辅助文案插槽/字段，并在四字段 Demo 只使用真正有助于识别的辅助信息。

**建议命令：**`/impeccable shape`

## 认知负荷

- [x] 单一焦点：组件主任务是设定筛选条件并查询。
- [x] 分块：折叠态前四项、状态带和操作组分块清楚。
- [x] 分组：标签、控件、状态/快捷键按近邻关系组织。
- [x] 视觉层级：查询为唯一主按钮，重置为次操作。
- [x] 一次一个决定：关闭确认独立成层，避免误触。
- [x] 最少选择：Demo 模拟模式为成功/空结果/失败三项，处于可控范围。
- [x] 工作记忆：当前结果状态与快捷键持续可见。
- [x] 渐进披露：超过 8 项时默认收起，其余条件按需展开。

认知负荷评定：低（0 项明确失败）。文档壳层在 375px 会把 API 长表格压缩得很密，属于文档阅读负担，不改变组件交互结论。

## 情绪路径

SearchBar 从等待到查询中再到成功/空结果/失败均有文字落点，失败后可重试，收尾是可预期的。StatusSwitch 在关闭前以确认层制造必要的停顿，取消后维持原状态，安全感成立；但高风险层缺少影响范围与审计上下文，风险峰值表达还不够有说服力。

## Persona 红旗

### Alex（高频管理台用户）

- SearchBar 的 Enter 查询、Esc 重置和折叠能减少鼠标往返。
- StatusSwitch 没有面向批量表格的快捷/批量路径；每行仍是单独切换和单独确认。
- loading 期间的锁定正确，但保存结果反馈由宿主提供，组件单独嵌入时需要额外编排。

### Sam（键盘/读屏用户）

- SearchBar 标签与 `role="search"` 清楚，375px 控件高度可操作。
- StatusSwitch Demo 的主要布控/旧值/确认行有 `aria-labelledby`，但 loading、只读、权限不足行没有稳定行名；fallback Tag 的通用文案不足以识别对象。
- 确认弹层有取消和可见焦点，但关闭后风险摘要太短，读屏用户得到的上下文少于设计稿。

### Casey（移动端用户）

- 375px 文档页无页面级横向溢出；SearchBar 操作区和 StatusSwitch 命中区域满足 44px 触控要求。
- SearchBar 四字段会自然单列，顺序可预测；状态带与按钮靠近组件底部，拇指操作路径合理。
- 文档壳层的长 API 表格与说明在 375px 纵向很长，首次定位交互示例需要滚动较久。

## 次要观察

- 浏览器控制台仅见 Vite 连接日志及 SearchBar 桌面页一次 404 资源；未把它作为组件视觉缺陷。
- SearchBar Demo 在初始等待态结果为“无结果”，与“尚未执行查询”的语义略有冲突；可改为“尚未查询”。
- StatusSwitch 的设计参考用 12px Spinner 和详细 loading 行文案，当前组件依赖 LxSwitch 内置 Spinner，宿主仍需提供“保存处理中/同步中”旁文案。
- 设计稿正文是大型规范标本，实际组件文档更轻量；两者对齐关系需要在 Demo 中用标准态明确呈现。

## 需要产品决定的问题

1. 高风险确认是否必须达到设计稿的完整影响摘要和审计提示，还是允许宿主只提供简短 `title/message`？
2. 行名关联优先覆盖全部状态（loading/disabled/permission），还是先覆盖权限降级和只读 Tag 两个高风险读屏场景？
3. SearchBar 下一轮优先补“四字段标准态”示例，还是先扩展字段图标/辅助文案契约？

## 证据限制

本次为独立 Assessment A，只读取目标源码、对应 Demo/文档、设计 HTML/PNG 和本次新建浏览器上下文的截图/DOM 指标；没有读取 Assessment B、detector 输出或代码审查输出。浏览器验证针对 VitePress 文档页，文档外壳、侧栏和 API 表格会影响截图密度；未建立单独的四字段最小宿主页面，也未进行真实后端、真实权限中心或真实读屏器联调。因此“四字段同行”主要由源码分支和文档对照判断，ARIA 行名结论来自静态属性与浏览器 DOM 观察。
