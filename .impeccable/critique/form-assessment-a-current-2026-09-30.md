## 设计特异性判断

整体与 LinkX/LxUI 有中等程度的关联：表单继承 Lx token、Element Plus 的业务习惯和节点管理弹窗的错误态规范；动态示例选用任务、责任网格、负责人等后台业务词汇。错误状态也有明确的统一实现。

但布局和组件语汇仍接近通用 Element Plus 管理后台表单，换成其他后台产品后大多可以原样复用。LxUI 的个性主要落在 token 和错误态细节，页面结构与使用流程没有形成更鲜明的 LinkX 特征。示例业务语境提供了可信度，尚未转化为更具辨识度的表单分组与任务顺序。

## 认知负荷

8 项检查有 3 项未通过，属于中等负荷：

- **单一焦点：未通过。** 动态示例的列数、禁用、主题、候选 Mock 状态控制都放在表单之前，和填写任务争夺首屏注意力。
- **分块：通过。** 列布局、候选状态、表单字段和操作区分别成组；各决策组不超过 4 个选项。
- **分组：通过。** 卡片边界、间距和候选状态小组能区分不同控件。
- **视觉层级：未通过。** 动态示例的配置按钮与“提交校验”都使用轻量描边样式，操作目的没有形成清楚的主次。
- **一次一件事：通过。** 字段按垂直顺序填写，校验后错误出现在对应字段。
- **最少选项：通过。** 列数有 4 个选项、候选状态有 3 个选项，均未超过单个决策点的 4 项上限；没有发现单个决策点超过 4 个可见选项。
- **工作记忆：通过。** 字段值保留在当前表单，不需要跨页记忆后再输入。
- **渐进披露：未通过。** 调试配置和 Mock 状态切换默认常驻；代码示例虽折叠，但配置操作没有收起或分层。

## 整体感受与情绪路径

页面先解释组件能力，再给出可操作示例，最后提供 API 和迁移细节，文档阅读路径清楚。提交空表单后的错误态是主要情绪低谷：红色字段边框、图标和字段文案让问题明确，输入仍在表单中，用户可以就地恢复。LxForm 额外出现“表单校验未通过”的顶部提示，提供了总体确认，但与字段内提示存在轻微重复。动态表单成功时仅证明校验通过而不表示数据已保存；当前文档说明请求由宿主负责，这个产品边界需要在接入示例里继续保持清晰。

## 做得好的地方

1. **错误态能落到具体字段。** 校验失败后，控件红边/浅红底、图标和文字一起出现；真实浏览器检查确认两种组件都保留了错误输入，诊断路径短。
2. **动态数据状态有可观察反馈。** 示例覆盖成功、空结果、加载、失败和重试，并明确标注候选数据为 Mock；用户能区分“没有结果”和“请求失败”。
3. **组件职责界线清楚。** 表单持有受控值和校验能力，网络请求与上传由宿主接入；迁移文档列出旧用法与实例方法，降低了现有业务迁移风险。

## 优先问题

### [P1] 自适应表单在文档容器中没有呈现承诺的双列布局

**为什么重要**：默认 `adaptive` 示例在文档约 600px 宽的演示卡片里实际显示为单列。文档说明容器窄于 760px 时应切到两列；业务读者会看不到所承诺的紧凑布局，也难以判断字段 `span` 是否有效。

**建议修复**：让字段占列数跟随当前有效列数重新计算，或让容器查询能覆盖字段的基础 span 样式；在 3/2/1 列状态分别展示一个半宽字段与一个通栏字段。当前 `fieldStyle()` 内联设置的三列 span 与两列容器查询存在优先级冲突的可能性，建议先核对这一处。

**建议命令**：`/impeccable adapt`

### [P2] 示例配置控制抢占动态表单的首屏焦点

**为什么重要**：首次到达示例页的人会先看到列数切换、禁用/主题开关和候选状态 Mock；这对组件评估有用，但把主要任务“填写并校验表单”推到第二层，且配置按钮与表单动作没有清晰的主次。

**建议修复**：把这些控件放进标题明确的“演示设置”区，降低视觉权重；把低频主题和 Mock 状态放在可展开的高级设置中，默认突出表单和校验结果。

**建议命令**：`/impeccable distill`

### [P2] 校验错误文字尺寸偏小，整体提示与字段提示略重复

**为什么重要**：样式把错误文字固定为 11px；桌面截图中它明显小于标签和输入内容。LxForm 还同时出现顶部校验通知和每个字段的错误文案，多个必填项失败时会形成重复提示。

**建议修复**：将字段错误文案提升到至少 12px，并验证错误色在浅红底上的对比度；保留字段级说明作为主要恢复提示，把顶部通知缩短为一次性摘要或移除重复内容。当前仅做了视觉判断，未进行对比度测量。

**建议命令**：`/impeccable clarify`

### [P3] “React/TSX 风格”措辞模糊了 Vue 文档里的受控值用法

**为什么重要**：组件页面和示例都是 Vue SFC，但简介把 `value + change(nextValue)` 称为 React/TSX 风格。读者可能误以为它是独立于 Vue 的运行方式；这让双受控契约比实际更难理解。

**建议修复**：用“受控值用法”说明 `value` 与 `change`，并给出 Vue 模板中的具体调用场景；如确实支持 TSX，再单独写明 TSX 语法，而不是把 React 与 TSX 合称一种契约。

**建议命令**：`/impeccable clarify`

## 人物视角的红旗

**Jordan（首次使用者）**：必填星号和“提交校验”让下一步可见，但仍需弄懂 `schema`、`adaptive`、24 栅格 `span` 以及 Vue 的 `v-model` 与 `value/change` 两套控制方式。首次接入者可能先把时间花在术语映射，而不是组装第一个表单。建议在示例上方给一个最小的“字段定义 → 表单呈现 → 收集变化”任务路径。

**Sam（依赖辅助技术的用户）**：AX 树能读到字段名称和实际错误文案，截图中错误也同时使用图标与文字，没有只靠红色表达。字段错误字只有 11px，视觉阅读负担偏高；本次没有做 200% 缩放、键盘全流程或真实 NVDA/VoiceOver 检查，仍需确认错误文案的实时播报和焦点位置。

**Alex（熟练用户）**：键盘可定位表单控件与“提交校验/重置”按钮；公开方法能支持业务快捷编排。组件文档没有说明 Enter 是否能直接触发校验，内联搜索示例则专门写了 Enter 触发搜索；高频表单接入者可能需要自己补充统一提交入口。

## 次要观察

- LxForm 的 11px 错误规格在文档里有明确视觉出处，建议用实测对比度和实际缩放结果确认小字号仍清楚。
- 动态示例支持 HUD 深色主题切换，但没有提供文档截图对比；评审只检查了浅色态。
- 文档右侧目录和左侧组件导航能帮助定位长 API 页面；具体参数仍以表格为主，移动端横向滚动与阅读体验未检查。
- 校验失败后的 LxForm 顶部通知是短暂反馈，字段文案是持久恢复提示；可继续保留两层反馈，但需要避免两者重复措辞。

## 值得追问的问题

- 自适应布局最重要的承诺是“自动适应容器”，还是“开发者能准确控制字段宽度”？能否让默认示例在首屏直接展示三列、两列和通栏字段之间的差异？
- 使用者第一次打开动态表单时，是否应该先看到一个真实可填写表单，再展开演示状态和主题设置？
- `value + change` 是否确有 React/TSX 消费者？如果主要是 Vue 调用方，如何让这条兼容契约一眼可懂？
