# LxTransferPanel 独立设计评审

**目标：** `http://127.0.0.1:4174/components/lxtransferpanel`，Operate 模式；评估范围是中文文档中的权限分配组件示例及其周边说明。

**整体判断：** 界面围绕组织树、已选权限和批量转移构建，业务语义清楚，窄屏操作也保持可用。主要摩擦在文档演示配置：默认紧凑档让桌面已选列表只显示一项；1024px 时待选标题被截短；窄屏高度选项表达的是目标高度，却受 352px 最小值约束。另有保存状态说明与主要交互入口距离较远的问题。

## 设计特异性

这是为组织权限分配场景设计的组件，不是可直接替换到任意表单的通用双列表。树结构、受控已选项、未加载历史项、下级继承、名额和批量反选共同对应权限管理任务。边界也写得明确：`modelValue` 是宿主传入的当前选择，不等于已保存；真实保存状态由宿主负责。

文档示例有意使用 240px 紧凑档，但组件 `panelHeight` API 默认值仍为 380px。当前选择器把 240px 标为“默认”，用户可能把示例默认值误读为组件默认契约；文档表格另有 380px 默认值，读者需要跨段落核对。

## 整体印象

权限分配的主任务和当前结果都能快速识别。可见数量、状态文本和“还有几项”的提示让用户知道清单并未结束。最明显的机会是让默认演示先呈现足够多的结果，并在切换面板前后都保留清楚的保存状态语义。

## 做得好的地方

- 桌面双栏把待选树与已选清单并列，中央批量操作说明“从哪一侧移到哪一侧”，初始已选数量和剩余名额也可见。
- 390px 与 320px 视口改为待选/已选切换，不发生页面横向溢出；切换按钮实测高 44px，适合触控。
- 长名称、未加载历史项、状态与继承说明均有明确表达；示例说明不调用后端，也不会把本地选择冒充真实授权或保存结果。

## 优先问题

### [P2] 紧凑默认让已选结果缺少首屏可见性

**现象：** 1440px 示例默认 240px 高时，已选列表可视区约 71px，4 项中仅完整显示 1 项；改为 300px 可见 3 项，380px 可见 4 项。390px 下 240px 与 300px 目标均受窄屏 352px 最小面板高度约束，所选面板可见 2 项，另外 2 项需要滚动。剩余项提示有帮助，但默认体验仍把大部分结果藏在滚动区。

**影响：** 第一次查看示例的用户需要主动滚动，才能核对大部分已选权限；演示容易显得比组件实际更拥挤。

**建议：** 将示例初始档设为 300px 或 380px；若保留 240px 紧凑示例，在高度选择器附近说明这是为展示紧凑状态，并保留“还有 N 项”的滚动提示。该建议针对文档 Demo，不建议据此改变组件 API 的 380px 默认值。

**建议命令：** `/impeccable adapt`。

### [P2] 1024px 下待选标题被截短

**现象：** 1024px 视口中预览宽 624px，待选标题区域约 110px；“组织与数据权限树（待选）”的可见标题被截短。DOM 中完整无障碍名称仍保留，未发现与右侧操作重叠。

**影响：** 视觉用户失去标题末尾的“树/待选”信息，界面需要依赖位置和图标推断面板含义。

**建议：** 在窄桌面断点允许标题换行，或把“更多反选选项”移至次行；也可采用更短但仍准确的可见标题，同时保留完整无障碍名称。

**建议命令：** `/impeccable adapt`。

### [P2] 窄屏高度选择显示目标值，实际面板有更高下限

**现象：** 390px 视口中选择 240px 或 300px，实际面板仍受 352px 最小高度约束；选择 380px 时才按 380px 显示。文档说明了该下限，但示例控件文案“面板高度 / 紧凑 240px / 适中 300px”容易让人期待实际尺寸与所选数字一致。

**影响：** 选择器反馈和窄屏实际布局不完全相符，尤其在高度有限的嵌入页面中会造成预期偏差。

**建议：** 把控件标签改为“面板目标高度”，并在控件旁显示“窄屏最小 352px”；保留 240/300/380 三档目标值及组件现有触控区约束。

**建议命令：** `/impeccable clarify`。

### [P2] 明确的未保存提示离“待选/已选”入口较远

**现象：** “待选/已选”切换与选择数量位于组件顶部；组件下方的短说明表示数据和错误恢复由宿主提供、示例使用本地内存，随后文档才明确说明“选择不代表权限已保存”。390px 与 320px 页面中，较完整的持久化说明位于示例内容下方，离主交互入口较远。

**影响：** 用户可能先把“已选”理解为已经分配或保存。这里的风险在权限配置语境下高于普通演示数据。

**建议：** 在组件示例旁紧邻“已选”区域显示“示例选择仅在本地内存，不代表已保存”；将较长的宿主职责和失败恢复细节留在下方文档。“待选”本身适合表示尚未加入的资源，不应承担未保存状态的表达。

**建议命令：** `/impeccable clarify`。

## 认知负荷

清单 8 项中 1 项未完全通过，整体为低认知负荷：

- 单一焦点：通过，用户主要在树与已选清单之间分配权限。
- 分块：通过，树、转移操作、已选清单和状态说明分区展示。
- 分组：通过，数据、筛选、数量和操作彼此邻近。
- 视觉层级：未完全通过，1024px 下标题被截短，紧凑默认也压低了结果可见性。
- 一次处理一件事：通过，窄屏一次只显示一个列表面板。
- 最少选项：通过，高度为三个档位，窄屏面板切换为两个选项。
- 工作记忆：通过，已选数量、待选数量和剩余名额都有可见反馈。
- 渐进披露：通过，批量反选的额外范围折叠；列表和长文本按需滚动或展开。

## 情绪旅程

用户进入后可见已载入状态和两侧任务分区；加入或移除时，数量与名额提供即时核对线索。紧凑视图及被截短的标题形成轻微的不确定感。文档后段解释保存边界和恢复责任，能建立信心，但出现得晚于选择动作本身；将一句“本示例未保存”移到组件旁，可以在产生误解前消除这段落差。

## 角色风险

**Alex（熟练管理员）：** 批量加入/移除、树搜索和虚拟滚动适合高频权限配置；默认 240px 只显示一条完整结果，增加反复滚动成本。完整键盘路径没有在本轮中实测，因此不判断其是否满足快捷操作预期。

**Sam（依赖辅助技术的用户）：** 1024px 视觉标题被截短，但浏览器证据中完整标题仍保留为无障碍名称。状态除颜色点外也有“正常”等文本。屏幕阅读器、键盘焦点顺序、200% 缩放和数值对比度未验证，不能据本轮下结论。

**Casey（移动用户）：** 390px 和 320px 下布局没有横向溢出，面板切换按钮高 44px；当前面板内部仍需滚动查看全部选择。明确的持久化说明在主要示例之后，离开或中断操作的用户需要继续向下阅读才能看到完整边界。

## 次要观察

- HUD 深色主题只作用于示例组件，浅色文档外壳保持稳定；两种主题下选中状态和文本层级仍可区分。
- 所有采集页面启用了减少动效偏好，组件过渡记录为近零时长。
- 12 个页面均未记录页面异常、失败请求或失败响应。桌面浅色页面记录到一次 `/favicon.ico` 404；它是文档站图标请求，不是组件请求。
- 1440、1024、390、320px 视口的文档宽度与页面滚动宽度一致，没有观察到横向溢出。

## 需要继续思考的问题

- 文档示例是否应默认展示 300px 或 380px，让已选结果更容易被核对？
- 高度选择器能否明确表达“目标高度”和窄屏 352px 实际下限？
- “已选”旁是否应直接标注“示例选择未保存”，避免用户把选择反馈误认为权限已提交？
