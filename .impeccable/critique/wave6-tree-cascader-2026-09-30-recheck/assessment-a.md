# LxTreeSelect 与 LxCascader 设计评审

## 设计特异性判断

这组控件在业务语境上有明确的 LinkX 管理台特征：杭州市公安组织层级、中文字段、32px 表单基线、克制的主色选中态，以及树节点与级联路径两种不同选择模型。用同一组组织数据对照树形节点选择和逐级路径选择，能直接解释“选一个层级节点”与“选一条完整路径”的差别，设计不是纯粹换肤的通用下拉框。

视觉语言仍主要依赖 Element Plus 的标准控件结构和 lx-ui 令牌，单看触发器和菜单可被其他企业后台复用；产品个性来自数据与交互边界，而非独特视觉表达。对高频后台录入控件而言，这种低调、清楚的取向合适，品牌表达不必盖过组织数据。

浏览器证据：使用 CUA 新建本地文档页 `http://127.0.0.1:4179/components/lxtreeselect` 与 `http://127.0.0.1:4179/components/lxcascader`。查看了初始页面、树的展开/多选 footer/加载/失败/HUD 深色，以及级联的展开、多选、加载和失败状态，并检查了可访问性树。当前环境未提供可设置浏览器视口的能力，因此 375px 窄屏未在浏览器实测；触控尺寸和横向滚动只按源码与文档记录评估。

## 认知负荷

**结论：中等，3 项失败。**

| 检查项 | 结果 | 证据 |
|---|---|---|
| 单一焦点 | 失败 | 组件字段前先出现多项示例状态开关，示例控制与被演示控件在同一区域竞争注意。 |
| 分块（每组不超过 4 项） | 失败 | TreeSelect 工具栏含单/多选、空目录、加载、失败、HUD；Cascader 同时呈现模式和四种状态。 |
| 视觉分组 | 通过 | 状态控件处于同一组，字段和值回显相邻。 |
| 视觉层级 | 通过 | 文档标题、示例、字段和 API 标题层级清楚。 |
| 一次一个决定 | 通过 | 选择控件各自承载一个主要决定；TreeSelect 将多选提交另行确认。 |
| 最少选项（每决策点不超过 4 项） | 失败 | 两个示例工具栏均有至少 5 个并列可选状态。 |
| 工作记忆 | 通过 | 当前路径和值回显在控件附近，无需记住上一屏选择。 |
| 渐进披露 | 通过 | TreeSelect 示例代码通过折叠区展开；API 细节位于后续区段。 |

## 情绪旅程

用户从带有具体组织路径的示例开始，容易理解控件的用途；TreeSelect 展开后显示节点、选中值和 footer 数量，确认或取消时有明确的控制感。加载与失败状态提供文字说明和恢复入口，错误不会变成空白字段。情绪上的低谷出现在了解集成细节时：演示页将多种测试状态并排摆出，之后 API 表又省略若干常用契约，读者可能不确定示例覆盖了哪些公开属性。结束时用户能看懂控件，却可能还要回 Element Plus 文档或源码确认具体接线方式。

## 做得好的地方

1. **两种选择模型有清楚分工。** 同一组织样例分别呈现任意树节点与完整级联路径，使用者能据任务选组件。
2. **TreeSelect 多选的提交边界明确。** 勾选先留在草稿，底部数量、取消和确认让结果可预期，也支持 Escape 丢弃。
3. **状态反馈有恢复路径。** 错误文案和重试动作同处一行；加载期间禁用 TreeSelect 确认，级联面板也显示加载文字并暂停选择。

## 优先问题

### [P2] Cascader 示例中的可见标签没有进入辅助技术名称

**为什么重要：** 浏览器 AX 树把示例字段显示为无名称的 textbox，虽然视觉上方有“组织路径”。屏幕阅读器用户无法从控件本身辨认用途，且文档基础用法示例也未展示标签接法。

**修复：** 让示例的“组织路径”标签与真实内部输入建立可验证的关联；若 Element Plus 的 `id` 透传不能形成标签关系，给内部字段提供 `aria-label` 或 `aria-labelledby`，并把推荐的表单标签接法写进示例。

**建议命令：** `/impeccable audit`

### [P2] TreeSelect 键盘焦点提示比 Cascader 弱

**为什么重要：** TreeSelect 样式将 focused wrapper 的 outline 与 shadow 都关闭，焦点主要靠 1px 边框变色；Cascader 则保留 2px token 焦点光环。两种邻近控件给键盘用户的焦点显著性不一致。

**修复：** 为 TreeSelect 保留符合 lx-ui 焦点令牌的可见 focus indicator，与 Cascader 的焦点边界统一；同时检查错误态焦点时的对比。

**建议命令：** `/impeccable polish`

### [P2] 示例工具栏把过多演示选项平铺为同级动作

**为什么重要：** TreeSelect 同时显示模式、空目录、加载、失败和 HUD 开关；Cascader 显示模式加四个状态按钮。首次读文档的人需要先辨认测试工具，真正控件反而排在后面。

**修复：** 将状态演示收拢为一个明确的“演示状态”选择器或分组，默认保留最有代表性的状态，并让当前字段仍是示例视觉中心。

**建议命令：** `/impeccable distill`

### [P2] API 文档没有形成完整、统一的公开契约表

**为什么重要：** TreeSelect 表格没有列出 `data`、`placeholder`、`filterable`、`multiple`、`size` 等基础属性，主要靠示例和“其他属性透传”补充；Cascader 表格也省略 `collapseTags`、`showAllLevels`、`emitPath` 等公开项。两个组件的可见事件名还分别写作 `visible-change` 与 `visibleChange`。组件库消费者需要来回查源码或 Element Plus 文档才能确认边界。

**修复：** 文档列齐 wrapper 声明的 props、默认值、事件、插槽和 expose；单独注明透传属性及其内核来源。统一可见事件命名，或在迁移兼容前提下明确列出两个名字对应的监听方式。

**建议命令：** `/impeccable clarify`

### [P2] 两个组件的状态语言与国际化边界不一致

**为什么重要：** TreeSelect 接受并继承 `locale`，而 Cascader 的空、加载和错误文案默认是硬编码中文。中文后台中没有问题，但同一个 lx-ui 宿主在非中文 locale 下会出现一半翻译、一半中文的反馈。

**修复：** 明确 lx-ui 是否只支持中文；若宿主 locale 可变，为 Cascader 提供一致的局部 locale/文案入口，并说明它与 Element Plus 全局 locale 的优先关系。

**建议命令：** `/impeccable clarify`

## Persona 红旗

- **Alex（高频用户）：** TreeSelect 文档说明了方向键、Enter 和 Escape，基本路径可走键盘；但公开方法与事件需在示例和后段 API 说明之间跳读。状态控制示例不是业务效率问题，不应误作真实用户流程。
- **Jordan（初次使用者）：** “树形下拉”和“级联路径”通过示例可区分，但第一次接入要理解 `node-key`、`value-key`、`emitPath`、`checkStrictly`、`$attrs` 等术语；缺少按场景挑选属性的短说明。Cascader 演示的 textbox 也缺少读屏名称。
- **Sam（键盘/读屏用户）：** TreeSelect 文档列出键盘操作且错误重试可聚焦，是正向证据；Cascader 示例 textbox 在 AX 树无名称，TreeSelect 焦点样式又弱于 Cascader，建议优先处理这两处。

## 次要观察

- 文档站侧栏长期展开大量组件链接，尤其“数据录入”项数较多；这属于整站文档导航负荷，不完全由本次两个页面造成。
- TreeSelect 示例回显原始值 `"bj"` / `["bj-1"]`，Cascader 同时呈现本地化路径和原始 key；统一回显格式能减少两页的比较成本。
- 当前代码为移动端触控目标提供 44px CSS 基线，Cascader 声明 375px 面板边界和内部横向滚动；本次未能在真实窄视口复核这些说明。

## 复验范围

修复后针对两页复核：键盘 Tab 焦点是否有稳定可见光环；屏幕阅读器名称是否读出 Cascader 字段标签；5 项以上演示状态是否收敛；TreeSelect 与 Cascader 的事件、文案 locale 和 props 文档是否一致。浏览器宽度需要在 375px 重新检查弹层是否留在视口内、级联列是否只在弹层内部横向滚动，以及触控目标是否达到 44px。

## 设计问题

- 如果默认示例只展示最常用路径，读者会不会更快理解组件，而把加载、错误与主题状态放入折叠的“更多状态”？
- TreeSelect 与 Cascader 是否应该共享统一的焦点光环、locale 和可见状态事件命名？
- 是否希望组件文档对“声明 props”和“透传 Element Plus 属性”提供一张完整、明确的边界表？
