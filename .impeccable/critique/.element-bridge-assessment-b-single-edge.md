The focused baseline is stable at 319×32px on desktop and 301×32px at 375px. Computed focus styling is a single 2px inset shadow: light `rgb(0, 96, 169)`, HUD `rgb(56, 189, 248)`. No separate outer focus halo was visible in these fresh-page baseline captures. The 375px page without the injected overlay had `documentElement.scrollWidth === 375`; the detector annotations can extend beyond the viewport and must not be counted as product overflow.

The bridge demo does not define validation rules for “协同部门”. Error captures therefore simulate the visual state by adding `.is-error` to its `.el-form-item` and `aria-invalid="true"` to the combobox, then capture the still-focused, closed control. They verify rendering only; a real form-validation error message and its lifecycle were not exercised.

The fresh HUD error-state computed-style check found a remaining styling defect. Focus remained on `input.el-select__input[role="combobox"]`; the popup was closed (`aria-expanded="false"`). The wrapper computed to `border-width: 0px`, `border-style: none`, `border-color: rgb(148, 163, 184)`, `outline: rgb(148, 163, 184) none 3px`, `box-shadow: rgb(56, 189, 248) 0px 0px 0px 2px inset`, and `background-color: rgba(245, 108, 108, 0.15)`. Thus there is only one computed shadow and no CSS outline/border stroke, but the focused ring stays cyan while the error background is pink; it does not become the documented single red error edge. The matching source selector `html:root .el-form-item.is-error .el-select__wrapper.is-focused` is present, yet did not win the rendered cascade in this host. This mixed-color error/focus state still needs a style fix. The baseline, non-error focus state is a single aligned ring.

## Overlay findings and attribution

The fresh desktop-light injection logged the console summary `[impeccable] 7 anti-patterns found` and eight detailed marker lines: `line-length` ×3, `layout-transition` ×2, `buried-raster` ×2, and `bounce-easing` ×1. The count in the helper's summary is preserved as emitted; it differs from its detail-line count. A separate fresh mobile pass emitted `[impeccable] 5 anti-patterns found` and six detailed lines, including a breakpoint-specific `clipped-overflow-container` marker.

- `line-length` markers point at the bridge page's Chinese Markdown prose. They are content findings, not controls. The ~86-character heuristic is not a direct measure of Chinese glyph width; the captured desktop paragraphs wrap at roughly 35–40 Han characters per line. Treat this as a weak readability signal, not a confirmed overlong visual line.
- `layout-transition: width` points to `.el-tabs__active-bar.is-top`, the Element Plus tab indicator. This is a real component-level rule match but belongs to the tabs example and does not involve the multi-select focus edge.
- The two `buried-raster` markers target VitePress `button.copy` controls under `.language-vue.vp-adaptive-theme` and `.language-ts.vp-adaptive-theme`. Their low-opacity raster is the copy icon hidden until hover, so these are documentation-shell false positives.
- The mobile `clipped-overflow-container` marker targets `span.container` inside `button.VPNavBarHamburger`. It is the three-bar VitePress mobile menu icon; no select, menu popover, or positioned child escaping that icon was found. Treat it as a shell false positive.
- The page-level `body` markers report bounce easing `cubic-bezier(.71, -.46, .29, 1.46)` and a height/padding transition. They have no affected `.el-select` target and are too broad to assign to the multi-select without separate stylesheet provenance.
- A subsequent async detector result also reported `text-occlusion` for the annotation text `layout property animatio` overlapping an Element Plus tab label. The text is the detector's own overlay label, so this is an overlay self-collision, not an application content collision.

No overlay finding targeted `.el-select`, `.el-select__wrapper`, or its focus selector. Across the inspected captures the bridge's multiple select held focus with the popup closed and retained its 32px height. This is browser evidence for the captured states, not a claim about every browser or an actual validation flow.

The page also emitted 19 Vue warnings with the repeated message `Component "" has already been registered in target app.` and one `Failed to load resource` 404 console error. They were not associated with the multi-select in this run. Vite emitted two connection debug messages.
