## Design Specificity Verdict

### LLM 评估

这是为 LinkX 权限分配场景定制的双栏组件：虚拟树、组织编码、在线/处理中/忙碌/停用状态、未知但仍可移除的既有键，以及“下级继承授权”共同形成了产品语境，整体不是可直接换皮的通用穿梭框。5:2:5 三列和 380px 面板把大量节点的扫描任务放在中心，视觉稿中的 `1,420` 节点、32px 行高和 4px 滚动条也让“密集管理工具”定位清楚。

当前运行示例与视觉稿之间有明显证据缺口。视觉稿展示了 1,420 节点、展开层级、滚动条、五条已选权限和动态穿梭说明；文档 demo 只有一个根节点和四个子节点，无法让读者看到虚拟滚动、长列表滚动或层级密度。浏览器页面还被 VitePress 侧栏压缩为 688px 内容区，标题和编码在真实宽度下更容易省略。文档说明本身是完整的，但 `code.html` 的 TypeScript 标本仍写着 `onNodeChange`、`onClearAll` 和“最大 400px”，而现行组件暴露的是 `update:modelValue`、`change`、`clear-all`，会削弱设计稿作为契约的可信度。

### 自动扫描

本次只执行 Assessment A。为保持 A/B 隔离，未运行 `detect.mjs`，因此没有静态 detector 计数、规则名称或 overlay 结果可报告；`browser-evidence.json` 记录的是独立浏览器实测，不是 detector 结论。

## Overall Impression

组件在桌面和移动端都保持了明确的双栏任务结构，尺寸、状态色和密度与公安警务权限场景相符。最大机会是把“高风险授权变更”和“数据暂未加载”做成同一条连续、可恢复的任务路径，并让文档 demo 真正展示视觉稿所承诺的虚拟大数据体验。

## What's Working

1. **结构约束明确。** `index.vue:438-447` 固定 5:2:5、36/45/内容/32px 行结构；浏览器实测桌面两面板等高 380px，375px 自动单列且无横向滚动，设计稿中的骨架被稳定落地。
2. **权限上下文没有被简化掉。** 左树同时显示编码和状态，右侧保留“当前树未加载”的 `legacy-unit-08` 并允许移除；选中计数、状态文字和禁用节点让颜色不是唯一语义来源。
3. **主题和可访问基础扎实。** HUD 令牌覆盖面板表面与文本；树行采用 roving tabindex、方向键和 Space/Enter；主要按钮、筛选框、删除按钮有可见焦点，`prefers-reduced-motion` 也有降级路径。

## Priority Issues

### [P1] 清空权限没有确认或撤销

**为什么重要：** 右侧“清空”和中间左箭头会立即移除全部选中键；这类权限操作的代价高，当前只有状态文字和 `clear-all` 事件，用户无法在误触后恢复。视觉稿甚至使用“一键清空”文案，进一步放大了危险感。

**修复：** 清空前显示轻量确认（保留数量和受影响范围），或提供短时撤销条；确认/撤销必须保留未知键和超限初始键的语义。逐项移除可继续即时执行，但应在删除按钮 tooltip 中明确对象。

**建议命令：** `/impeccable harden`

### [P1] 加载和错误替换整个面板，任务上下文断裂

**为什么重要：** 示例 `basic.vue:133-150` 在加载/失败时用一块 96px 消息替换双栏，用户看不到当前选择、筛选词和重试影响范围；错误只剩“加载失败”和“重试”，选中数量在面板外孤立显示。真实网络慢时这会让用户误以为授权状态丢失。

**修复：** 保留两侧面板外壳和标题，给左树内容加 `aria-busy`/骨架或遮罩；错误原位覆盖数据区，保留已选列表和筛选词，重试后恢复焦点。将“宿主负责加载/错误”在文档中配一个不破坏上下文的推荐包裹模式。

**建议命令：** `/impeccable harden`

### [P1] 文档示例无法证明视觉稿承诺的虚拟大数据能力

**为什么重要：** 当前 demo 的 `treeData` 只有一个根和四个子节点，380px 树区没有滚动；读者无法验证 1,420 节点、虚拟渲染、长层级和滚动条密度。设计稿的关键卖点因此只停留在静态图片里。

**修复：** 增加本地生成的长树（稳定 1,420 个节点，含长文本、禁用、状态和选中分布），默认展开少量分支并让树出现真实滚动；保留轻量数据生成函数和空/错误切换，避免把接口 Mock 当生产实现。将视觉稿中的代码契约更新为现行 Props/Events，或明确标注为历史标本。

**建议命令：** `/impeccable polish`

### [P2] 面板语义和触控尺寸不完整

**为什么重要：** 两个面板标题是普通 `span`，没有与树/列表建立 `aria-labelledby` 的组语义；中间箭头虽然有 `aria-label`，但视觉上只给图标。375px 下源面板“全选/反选”、右侧“清空”和 24px 筛选清除按钮低于 44px 触控目标，低视力/手指操作用户更容易误触。

**修复：** 用唯一 id 将面板标题与 `role="group"` 关联，树和列表继续保留已有 aria-label；为中间动作提供短的可见辅助文案或在窄屏使用带文字的垂直按钮；移动端将可操作目标统一提升到 44px，右侧筛选提供清除按钮。

**建议命令：** `/impeccable audit`

### [P2] 窄宽度下元数据与任务控件争夺注意力

**为什么重要：** 编码和状态使用 10px 字体并同时占据右侧列表空间；在文档内容区 688px、尤其 375px 下，长名称更早被省略，状态信息变成难扫描的小标签。demo 工具栏还把四个状态按钮、数量限制和 HUD 开关放在同一决策点，增加认知负荷。

**修复：** 保留名称为第一视觉层级，编码/状态在 375px 改为第二行或折叠详情，保持可访问名称完整；将 demo 状态切换放入“场景”折叠区，默认只显示正常态与主题开关。生产组件可保留密集模式，但应给宿主一个可选的元数据展示策略。

**建议命令：** `/impeccable layout`

## Cognitive Load Assessment

结论：**中等负荷（3 项失败）**。双栏本身是合理的并列任务，但 demo 和窄屏同时暴露了较多动作。

- **分组：通过。** 左树、中心批量操作、右清单有边界、标题和 footer，空间关系清楚。
- **视觉层级：部分失败。** 组件内部主次明确，但 demo 顶部六个状态/设置选项视觉权重接近；10px 编码/状态与主名称竞争横向空间。
- **一次一事：失败。** 用户在同一视图同时处理树搜索、树选择、批量移动、右侧搜索、逐项删除和继承开关；这对熟练管理者可接受，对首次使用者需要更多引导。
- **最少选择：失败。** demo 决策点可见 6 个工具选项，超过 4 项工作记忆基线；组件本身也有全选、反选、两个箭头、清空和继承开关等 6 类动作。
- **工作记忆：通过。** 已选数量、编码、状态和未知键持续显示，不需要记住上一屏结果。
- **渐进披露：通过。** 代码/状态只在节点有值时出现，tooltip 承载完整文本；但文档规则和 API 表集中堆叠在示例下方，阅读段落较长。
- **多任务需求：失败。** 双侧过滤与中间移动需要来回扫视；右侧搜索没有清除动作，会增加一次额外编辑步骤。
- **上下文切换：通过。** 选择与结果同屏，清空/重试不需要离开页面。

## Emotional Journey

- **进入：** 标题、组织树、已选清单和主色箭头让用户很快理解“从左向右授予权限”，视觉稿与运行页面都建立了可信的管理工具基调。
- **完成一次选择：** 右侧计数、状态点和实时状态文案形成正反馈；未知选中键仍可移除，减少数据未加载时的焦虑。
- **情绪高点：** 批量加入后右侧清单即时增长，HUD 模式在深色值守场景下有明确的产品气质。
- **情绪低谷：** 清空无确认、达到 `maxCount` 只出现 toast，以及加载/错误时面板被替换，都会让高风险操作和网络波动显得不可逆。
- **结束：** 空态文案能指向左侧勾选，错误有重试；若把原位状态和撤销补齐，结束感会从“我希望没有丢”变成“我知道下一步”。

## Persona Red Flags

### Alex（权限管理熟练者）

- 有全选、反选、批量箭头和双侧搜索，主任务可在一分钟内完成。
- 没有键盘快捷键把焦点选中项直接加入/移除，也没有批量撤销；Alex 仍需在两个搜索框和中心箭头之间移动焦点。
- 清空是不可撤销的即时动作，误按后只能重新遍历树恢复；达到上限时 toast 还会打断连续批量操作。

### Sam（键盘/读屏用户）

- 树行采用 roving tabindex，方向键和 Space/Enter 可选择，焦点轮廓实测可见；这是可用基础。
- 面板标题只是普通文本，未与 `role="tree"` 和 `ul` 通过 `aria-labelledby` 关联；读屏用户进入区域时只能听到“待选资源树/已选资源列表”，无法获得两侧完整标题和动作上下文。
- 宿主在加载/错误时用 `v-if` 替换整个组件，焦点目标被销毁；重试后没有明确焦点回归位置。清空的 destructive 语义也没有确认提示。

### Casey（375px 单手移动用户）

- 两个 380px 面板纵向排列，无横向溢出；中间箭头和删除按钮达到 44px，触控主路径可用。
- 页面需要连续上下滚动 840px 的组件高度，主动作位于两面板之间，单手返回右侧结果需要较长滚动距离。
- “全选/反选”32px、右侧“清空”32px、筛选清除24px 小于 44px；10px 编码/状态在窄屏阅读困难，demo 顶部六个选项也会挤占注意力。

## Minor Observations

- 左侧过滤输入有清除按钮，右侧过滤输入没有对应按钮；两侧行为不对称。
- 当前状态文案使用 `aria-live="polite"`，但 maxCount 警告来自全局消息，不一定与当前焦点建立关系。
- 视觉稿左标题使用选择态方块、右标题使用绿色状态点；现行组件使用 folder/check 图标。两者都能表达分区，但若要保持标本识别度，建议统一图标语义。
- 视觉稿写有“动态勾选自动穿梭”，实现实际保留双栏和中间批量动作；文档应明确是“同步到右侧清单”还是“自动移动 DOM”，避免读者按字面期待自动移位。
- `panelHeight` 会在组件内部最小化到 240px，但文档只说明目标高度 380px；自定义较小高度时建议把可用范围写出来。

## Questions to Consider

- 清空权限是否应该成为必须确认或可撤销的高风险动作，而不是与普通移除共用即时路径？
- 视觉稿把 1,420 节点和虚拟滚动作为核心卖点；文档 demo 是否应该默认让用户看到真实滚动，而不是只展示五个样例节点？
- 在 375px 下，编码/状态应始终并列显示，还是应让名称优先并把元数据放到可展开的第二行？

## 结论

28/40（Good）。组件的布局骨架、状态语义、主题令牌和基础键盘支持已经达到可用水平。发布前优先补清空的可恢复性、加载/错误时的上下文保留，以及能证明虚拟大数据能力的文档样例；随后再处理面板 ARIA 关联、移动触控尺寸和元数据密度。

Questions skipped: 本文件是独立 Assessment A 交付，针对用户的优先级问题由父任务在 A/B 综合报告中统一提出。
